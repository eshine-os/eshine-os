# 追了四个站的 1/10 闪断,真凶是一行裸 putc

(eshine-os 从零打造记 · 第二十二站)

我们有个悬案追了四个站:门禁里 vm1 的 spin 判据,大约每十轮
闪断一次,超时等不到 "spinning...",客机全程健康。三个历史案
例签名一致,两次专设的"观察哨"都没能复现。这次开站我按调试纪律
重走取证,第一步就挖出了被自己掩埋的关键证据。

## 第一步:重读错误信息,别 tail

TimeoutError 自带全量 output dump——上一站我处理它时只看了
最后 12 行,把真正的证据埋掉了。这次全量重读,发现 `spinning...`
根本不是缺席,是被撕成了这样:

```
vm1> spin
spinni[vm2] [   n 0.1339g17] CPU feature
```

vm1 的 "spinni|n|g" 和 vm2 的 Linux 时间戳 `[    0.133917]`
互相嵌进了对方字符串中间——vm2 的数字里嵌着 vm1 的 n 和 g。
read_until 找的是连续字节序列,当然永远找不到。三案全部同签名,
机制一次解释完:判据不是"没等到",是"字节被撕了"。

## 根因:锁图里的漏网之鱼

读 console.c:console_puts 持锁,console_putc 不持锁——原语级
的裂缝。全树一盘点,vuart 的前台透传路径(每来一个字符一次
MMIO 陷阱、一次裸 putc)是唯一高频裸写者:vm1 在 cpu0 上逐字符
裸写,vm2 在 cpu1/2 上持锁整行输出——锁拦不住锁外的写,两流
字节级互撕。更早两轮加锁(18D 和 [41] 家族修复)都把这条路径
漏了。

## 修复,以及修复引入的新撕裂

失败测试先行:vm2 靴流窗内 60 发 needle 行的风暴探针,修复前
4+ 撕。修三层:原语持锁(全类一次治)、前台改行缓冲('\n' 时
锁内整行原子)、停泊冲刷保键回显即时性。输出行 0/60 碎。

然后,自己的门禁抓住了我:A 轮在 [74] 复活链炸出新撕裂——
`[vm0] rtos> c[vm0] pu1: online`。机制:per-VM 的行缓冲被该
VM 的两个 vCPU 共享,我在主核停泊时冲刷半行,恰好把次核正在
追加的 "cpu1: online" 行拦腰切断。旧代码没这毛病:整行粘着
提示符一次出,needle 反而是连续的——我的冲刷差点成为下一个
真凶。修:全 VM 静默判(同侪 vCPU 都停泊才冲)。定点探针验证
needle 连续 1/1。

这条教训值得单独记:修并发 bug 时,你新引入的路径(这里是
"停泊即冲刷")会和旧路径共享同一份状态(这里是 per-VM 行
缓冲),不把共享面盘清楚,新路径就是下一个雷。

## B 块:软定时器

站二十一调研候选的头名:超时机器的定时器化。rt_timer_t 静态池,
回调跑在核 0 的 tick-ISR 语境——这里有个漂亮的契约可以引用:
我们的自旋锁持锁即屏本核中断,所以 ISR 永远不可能在持锁任务上
再入(同核自旋死锁在架构上不存在),打印原语天然 ISR 安全。
swtdemo 三面判据:单发到点、周期×3 自停、取消后的"缺席"本身
就是判据。

收口:门禁 75→76,A+B 终构建连续两轮全绿,观察哨闭案撤销。
残余如实入册:chardev 分块边界处的回显仍可能碎(当前判据面
零暴露,根治需要 100Hz 宿主时钟,列远期)。
