# 站 68F:幽灵出生链封口——向量表指认了站 28 的日生缺口

> 本站口径:README 案例纪要版。技术细节见
> docs/devlog/2026-11-06-station68-ghost-birth-chain.md。

## 案情

用户进 rtos shell 按下回车,内核 panic:`bookkeep violation`,
"有毒"的栈指针每次开机都是同一个值。verify 门 [19](RX 唤醒链)
100% 定复现。这不是竞态抖动——跨靴同值意味着某个确定性机制
在每靴同一位置落子。

## 仪器战争

十七件法医仪器逐面排查:任务字段五元组、簿记臂点、EL0 复活
usp 窗、EL2 存还面(TPIDR 逐陷阱存还+核号钳位)、四处蹦床臂
复核、tick 证据环、fork 检查点、as_copy 检测器……全部静默。
每件仪器淘汰一个假设,直到案卷只剩一个问题:

**违例帧的 psr 恒为 EL1t("内核以 SP_EL0 库为活栈"的语境戳),
而现场 spsel 读数恒为 1——"矛盾"?**

不是矛盾,是取景错误:psr 是被中断语境的存照,spsel 是处理语境
的现值,同一场异常的两张脸。而"谁在用 SP_EL0 库当活栈跑内核"——
ARM 向量表的第四个入口自己回答了这个问题。

## 出生链(五步定谳)

1. EL0 任务陷入系统调用,内核处理语境切换为 EL1+SPSel=0,
   活栈=SP_EL0 库(=任务自己的内核 C 栈);
2. 系统调用边界开中断;
3. 时钟节拍落在 C 处理中:异常取自"EL1+SPSel=0",硬件选中
   **"Current EL, SP_EL0" 向量槽**——但表里这个槽直通通用
   IRQ 入口,入场又强制 SPSel=1,于是 272 字节的中断帧被压上
   **32 字节的蹦床**;
4. 簿记把蹦床地址写进任务的 saved-sp——毒注入完成;
5. 该任务日后被复活:eret 携带 EL1t 存照回到 SPSel=0 语境,
   而此刻 SP_EL0 库里驻着别人的用户栈——**幽灵以别的任务的
   用户栈跑内核 C 代码**;下一个节拍又取同一个槽,又压蹦床,
   自我复制,地址确定性=跨靴同值。

站 28 交付 EL0 壳时,向量表只接了两种入口(EL0 来的、EL1h 来
的);"EL1 用 SP_EL0 库时来的中断"是第四种,一直裸奔到今天。
早期单核窄窗难得踩中;SMP 与 EL0 负载把它变成必踩,守卫把它
变成响亮的第一案。

## 修真(两件配对)

- **改道**:第四入口专设 `guest_irq_sp0`,先把栈库渡回被中断
  任务自己的内核 C 栈再压帧——帧满嵌套在任务栈域,簿记存值
  合法;
- **库还**:复活 EL1t 目标时,把帧顶(恰=压帧前的活栈)预还
  SP_EL0 库——否则弹栈在 SP_EL1 推进、SP_EL0 驻着残留,幽灵
  换个姿势复活。

## 洋葱下一层:次核失踪案(root-e)

修好出生链,全量再跑,门 [35] 又死:vm0 次核整靴从未上岗。
验证脚本 4/4 死,手动探针 14/14 活(同二进制同 QEMU 命令)。
这次靠三件仪器定案:QEMU -d int 中断流(次核专泵的物理核
整靴 28 个事件=纯睡眠水平,零 guest 执行;全靴 PSCI 调用零次
=上线调用根本没发出)、接缝字节(LOG 行不是丢了是没发出来)、
harness 骨架内交互二分(保留原前奏死/换探针前奏活)。

真凶=击键时机:验证在开机横幅后即把回车送进 RX 环,此时
RTOS 未开中断,回车挂起等门;门一开立即注入,落点恰在引导
尾最后几行(打印→LOG→次核上线调用→idle 入口)。回车唤醒
shell 在 IRQ 出口切走引导语境——被切走的引导语境=idle 伪
任务,上一案(root-a)的入队硬门令其永不复活=引导尾永久孤
儿化;系统其余一切照常(最后一个让出者自动变成 idle),看
起来完全健康。最讽刺的一环:旧验证能过这门的真相=root-a
之前 idle 会被入队迟到复活——修好上一案揭掉遮盖,68C 守卫
又把新病遮了三十六小时。

修真一行:开中断的调用挪到引导尾之后(次核同形)。引导尾
整段不可抢占,挂起输入在 idle 入口放行=落点语境已完整。
