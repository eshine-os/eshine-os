# 追了三个月的 panic,真凶是向量表上一根没接的线——eshine-os 站 68F 结案记

## 一个"不可能"的现场

我们自研 RTOS(跑在自研 type-1 hypervisor 上的 EL0 微内核壳)
有个顽固 bug:进 shell 按回车就 panic,守卫报"簿记违例"——
某个任务的 saved 栈指针落在了蹦床区,**而且每次开机都是同一
个地址**。

跨靴同值,这是最重要的指纹。竞态不会给出确定性的地址;能给出
确定性地址的,是某种"每靴在同一位置发生"的机制。问题是什么
机制。

## 仪器战争:十七件仪器,淘汰十七个假设

法医式排查一轮接一轮:字段五元组毒化(排除)、簿记写臂点
(排除)、EL0 复活的 usp 窗(排除)、EL2 hypervisor 的存还面
(逐陷阱存还+核号钳位,排除)、四处蹦床臂复核(全绿)、tick
证据环、fork 四检查点、as_copy 变化检测器……全部静默。

每件仪器淘汰一个嫌疑人。到最后,案卷里只剩一个"矛盾":

- 违例现场读出的异常帧 **psr=EL1t**——意思是"被中断时,内核
  正在用 SP_EL0 库当活栈";
- 而现场读 **spsel 寄存器=1**——SP_EL1 库才是当前选择。

一个上下文怎么可能既用 SP_EL0 又用 SP_EL1?我们一度怀疑
hypervisor 的 eret 恢复出了"混合态",甚至设计好了下一件仪器。

后来发现:**这不是矛盾,是取景错误**。psr 是"被中断语境"
的存照,spsel 是"处理语境"的现值——同一场异常的两张脸,
各说各话,本无冲突。真正该问的是:**到底谁在用 SP_EL0 库
跑内核代码?**

## 向量表的自白

ARM64 的向量表有 16 个槽,按"异常从哪来"+"当时用的是哪个
栈"分格。我们的 RTOS 在 EL1 用双栈库设计:内核任务跑 SP_EL1,
而 EL0 任务的系统调用处理跑 **SPSel=0**(活栈=SP_EL0 库=
任务自己的内核 C 栈,SP_EL1 库驻着 32 字节的蹦床,给下次
EL0 异常存 scratch 用)。

于是当系统调用处理中(开着中断)落下时钟节拍:

- 异常取自"EL1+SPSel=0"→ 硬件选中 **"Current EL, SP_EL0"
  向量槽**;
- 而我们的向量表里,这个槽直接接了通用 IRQ 入口;
- 硬件入场又强制 SPSel=1——于是 **272 字节的中断帧被压上了
  32 字节的蹦床**,压进邻域数据;
- 如果这个节拍决定切换任务,簿记把"帧地址"写进任务的
  saved-sp——**蹦床地址注入了任务上下文**;
- 该任务日后被调度复活:eret 携带 psr=EL1t 回到 SPSel=0
  语境,而此刻 SP_EL0 库里驻着**别的任务的用户栈**——
  幽灵以别人的用户栈跑内核 C 代码;
- 下一个节拍又从同一个槽进来,又压蹦床,又注入——**自我复制,
  地址确定性=跨靴同值**。一切指纹吻合。

站 28 交付 EL0 壳时,向量表只接了两种入口(EL0 来的、EL1h
来的);"EL1 用 SP_EL0 库时来的中断"是**第四种入口**,一直
裸奔。单核时代窗口极窄;SMP+EL0 负载把它变成必踩。

## 修真:两件配对

1. **改道**:第四入口专设 `guest_irq_sp0`——先渡回 SP_EL0 库
   (被中断任务自己的内核 C 栈)再压帧。帧满嵌套任务栈域,
   簿记存值合法,守卫恒绿。
2. **库还**:复活 EL1t 目标时,把帧顶(恰=压帧前的活栈)预还
   SP_EL0 库。否则弹栈在 SP_EL1 推进、SP_EL0 驻残留——幽灵
   换个姿势复活。

修复后:追捕以来每次必炸的 verify 门 [19](RX 唤醒链,恰是
"节拍落在 shell 处理中"的活证)首次转绿。但全量再跑,下一道门
又死了——修好一层,剥出下一层。

## 洋葱的下一层:次核失踪案

门 [35] 开始失败:vm0 的次核整靴从未上岗。验证脚本 4/4 死,手
动探针 14/14 活——同一二进制、同一 QEMU 命令。这一次靠三件仪器
定案:

1. **QEMU -d int 中断流**:次核专泵的物理核整靴只有 28 个事件,
   与纯睡眠的核一样多——次核代码从未执行过;全靴 PSCI 调用
   (hvc#0)零次——**"次核上线"的调用根本没发出**。
2. **接缝字节**:引导打印 "rtos: up" 的下一行直接是 initmark,
   中间该有的 LOG 行干干净净地不存在——不是传输丢了,是根本
   没发出来。
3. **harness 内二分**:在验证脚本骨架里替换前奏——保留原交互
   死,换探针式前奏活。

真凶是**击键时机**:验证脚本在看到开机横幅后就把回车送进了
RX 环——此时 RTOS 还没开中断,这个回车就"挂起等门"。几秒后
引导代码走到开中断的那一行,门一开,挂起的回车立即注入,落点
恰好砸在引导代码的最后几行(打印→LOG→**次核上线调用**→进
入 idle 循环)。回车唤醒了 shell,调度器在 IRQ 出口把引导语境
切走——而被切走的引导语境是 idle 伪任务,**root-a 修真(站 68
上一案)的入队硬门让它永不复活**:最后几行引导代码永久孤儿化。
系统其余一切照常(最后一个让出者自动变成 idle),次核却永远
没有上线,而旧验证之所以能过这一门,是因为 root-a 之前 idle
会被入队迟到复活——修好上一案,揭掉了遮盖,露出这一案;而
68C 守卫让验证在更早的门死掉,又把这个新病遮了三十六小时。

修法很小:**把开中断的调用挪到引导尾之后**——引导最后几行
整段不可抢占,挂起的输入在 idle 入口放行,落点已无害。

## 三条结案陈词

1. **守卫即战果**。没有 68C 域检,这是又一个"玄学偶发挂"
   躺着过站;有了守卫,出生点三小时内指认。为可疑不变量装
   门口哨兵,是值得的常驻税。
2. **"悖论"先查取景框**。psr 与 spsel 的"矛盾"曾把我们带偏
   一整轮。存照与现值、A 与 A 的记录,先分清两者各属哪个语境,
   再谈结论。
3. **槽位即语境**。向量表的槽是 CPU 提供的完整谓词——"从哪来
   +当时用什么栈"。双栈库设计的内核,四种入口一个都不能裸奔。
