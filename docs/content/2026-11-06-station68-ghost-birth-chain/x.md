1/ 三个月的 panic 今天结案:进 shell 按回车就炸,"有毒的"栈指针每次开机都是同一个地址。十七件法医仪器逐面排查后,自白书来自一个没人看的地方——ARM 向量表的第 23 行。🧵

2/ 指纹先读对:跨靴同值≠竞态。竞态给抖动,确定性地址意味着某个机制每靴在同一位置落子。要找的不是"谁写坏了",是"什么设计每靴必经此处"。

3/ 最大干扰项是一个"悖论":违例帧 psr=EL1t(被中断时内核在用 SP_EL0 库当活栈),而现场 spsel 读数=1。一个上下文怎么可能用两个库?——它没有。psr 是存照,spsel 是现值,同一场异常的两张脸。取景框装错,证据就全是噪声。

4/ 我们的 RTOS 是双栈库设计:内核任务跑 SP_EL1;EL0 任务的系统调用处理跑 SPSel=0(活栈=SP_EL0 库),SP_EL1 库驻 32B 蹦床。系统调用边界开中断——节拍这时落下来,异常取自"EL1+SPSel=0",硬件选中向量表 "Current EL, SP_EL0" 槽。

5/ 而那个槽,自站 28 起,直通通用 IRQ 入口。硬件入场强制 SPSel=1 → 272B 中断帧压上 32B 蹦床 → 节拍若切任务,簿记把蹦床地址写进 saved-sp。毒注入完成。任务日后复活:eret 携 EL1t 回 SPSel=0,而 SP_EL0 库里驻着别人的用户栈——幽灵用别人的栈跑内核 C。

6/ 下个节拍又取同一个槽,又压蹦床,又注入:自我复制,地址确定性=跨靴同值。站 32 调试时"打出的恰是别家函数的字面"、站 68 取证的"复合帧",全是一条链的下游。日生缺陷,单核窄窗,SMP+EL0 负载后成必踩,守卫让它成为响亮第一案。

7/ 修真两件配对:①第四入口专设 guest_irq_sp0,渡回被中断任务自己的内核 C 栈再压帧;②复活 EL1t 目标时把帧顶预还 SP_EL0 库(压栈在哪,复活回哪)。修复后追捕以来每次必炸的 verify 门 [19] 首绿。但全量再跑,下一道门又死了——修好一层,剥出下一层。

8/ 中间教训先记三条:守卫即战果(没有它,这是又一个躺着过站的玄学挂);"悖论"先查取景框再谈结论;向量表的槽位是 CPU 给的完整语境谓词,双栈库内核的四种入口,一个都不能裸奔。
9/ 洋葱剥出下一层:门[35] 死=次核整靴没上线。同二进制同 QEMU,验证脚本 4/4 死,手动探针 14/14 活——这次不猜,harness 骨架内做交互二分,真凶=击键时机。

10/ 验证脚本看到开机横幅就把回车送进 RX 环——RTOS 还没开中断,回车挂起等门。几秒后引导代码走到"开中断"那行:门一开,挂起的回车立即注入,落点恰好砸在引导尾最后几行(打印→LOG→次核上线调用→进 idle 循环)。-d int 定谳:CPU3 零 guest 执行,全靴 PSCI 调用零次——上线调用根本没发出。

11/ 回车唤醒 shell,调度器在 IRQ 出口把引导语境切走。被切走的引导语境=idle 伪任务,上一案(root-a)的入队硬门让它永不复活=引导尾永久孤儿化。系统其余一切照常(最后一个让出者自动变成 idle),看起来完全健康。

12/ 最讽刺的一环:旧验证能过这门的真相=root-a 之前 idle 会被入队迟到复活。修好上一案揭掉遮盖露出这一案;68C 守卫让验证在更早的门死掉,又把这病遮了 36 小时。每修一层,剥出下一层被遮蔽的病。

13/ 修法一行:把开中断的调用挪到引导尾之后。引导最后几行整段不可抢占,挂起输入在 idle 入口放行——落点语境已完整,被切走也只丢 idle 本体(良性)。次核上线调用从此不缺位。
