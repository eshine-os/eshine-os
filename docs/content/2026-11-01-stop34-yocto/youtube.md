# 站34 · YouTube 口播稿

**[开场]**
今天这一站,eshine-os 第三十四站,做 yocto 集成——把一个
能跑真 musl 的 hypervisor 和 RTOS,装进正经构建系统。但今天
真正的标题不是"我们做了什么",而是"什么没有发生":一场
六十枚补丁的战争,这一次没有发生。

**[战争为什么没来]**
先说背景。参考实现——我们只做机制参考的参考实现——他们的
yocto 集成带着大约六十枚工具链切换补丁:为了让 yocto 的
构建体系接受他们自己的工具链,他们和构建系统打了一场仗,
战果以补丁的形式永久驻扎在树里。

我们这边,这场仗没有开打。不是绕过去了,是没开战。因为
我们的 Makefile 从第一天起,工具链前缀就是一个环境变量:
CROSS 问号等于。配方里一行注入,层配置里四行,把宿主的
交叉 gcc、ld、objcopy、ar 加进 bitbake 的 HOSTTOOLS 白名单。
结束。六十枚补丁对两行配置——差的不是技术,是第一个
Makefile 落笔的时候,有没有问过自己:这个值,以后要不要换?

更深一层:我们的构建从来就是 freestanding——自带头文件,
零 libc 依赖。没有 glibc headers 要纠缠,没有 sysroot 要
打架。那六十枚补丁要解决的每一个问题,在我们的架构里
根本不存在。架构干净,构建面自然干净。

**[纪律反咬自己一口]**
这一站镜像了参考实现里最漂亮的一条机制:构建吃的是 git
archive HEAD 出来的源码包——提交树,不是工作树。同一提交,
任何时候构建,同一个结果。

结果这条纪律第一天就咬了我一口。部署配方要校验 LICENSE
文件,QA 当场拦下——因为 LICENSE 是我这一站刚写的新文件,
还没提交进历史,归档出来的 tar 里根本没有它。修复不是绕过
校验:把 LICENSE 老老实实先提交进历史,再重新归档。构建
系统拒绝构建未入库的源——这条纪律从此有了机器背书。第二
枚皱褶也是 QA 如实拦的:tar 自带顶层目录,配方里又写了个
subdir,两层一叠,文件深了一层。二选一,去掉 subdir。两枚
皱褶,零绕过,构建系统的 QA 诚意白嫖了两道。

**[判据:产品要真的能跑]**
构建集成最常见的自欺,是止步于"bitbake 跑通了"——任务
全绿,宣布胜利。我们不认这个账。新增的第九十三门是这样
的:门禁自己调 bitbake,拿到部署目录,然后用第二台 QEMU,
把部署出来的 eshine.elf 和 rtos.bin 启动起来,进 shell,
跑 run 斜杠 bin 斜杠 hello——上一站的 musl hello 在构建
系统产出的二进制上跑出同样的两行,收尸码归零,这门才算
过。验证的是产品,不是构建系统自嗨。从今天起,每一轮
门禁都顺带证明一次:yocto 出的活,能跑真 libc。

**[结尾]**
最后算一笔体量账:参考实现的 yocto 树七十六 GB,里面沉淀着
六十枚补丁和它们全部的历史;我们这边,poky 上游净克隆,
加上仓里四个文件的一个层、两个装配脚本。构建系统的体量,
应该来自上游,不是来自补丁。九十三门,两轮全绿。下一站,
docker 收出货。代码 Apache-2.0,我们下站见。
