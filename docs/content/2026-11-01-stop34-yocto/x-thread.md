# 站34 · X 9 连推

## 推 1(总览)
yocto 构建面落地:仓内即层(meta-eshine,4 文件),一条
bitbake eshine-rtos 从 git archive 提交树构建到部署四件。
判据=部署产物真实可靴:门禁第二台 QEMU 吃部署物跑 musl。
93 门 ×2。

## 推 2(零补丁)
参考实现的 yocto 集成带着 ~60 枚工具链切换补丁——一场与构建
系统的战争。我们零补丁:CROSS ?= 环境驱动+HOSTTOOLS 白名单
四件。六十对两行,差的是第一个 Makefile 落笔时那个问号:
这个值以后要不要换?

## 推 3(深层原因)
我们的构建从第一天就是 freestanding:自带头文件,零 libc
依赖。没有 sysroot 纠缠,没有 glibc headers 战场——六十枚
补丁要解决的任何问题,我们一个都没有。架构干净,构建面
自然干净。

## 推 4(纪律反咬)
"构建吃提交树"(git archive HEAD)是本站镜像的机制。结果
第一天就咬我:LICENSE 刚写还没进历史,tar 里没有它,
populate_lic QA 拦下。修=先提交再归档。构建系统拒绝未入库
的源——纪律有了机器背书。

## 推 5(第二枚皱褶)
源 tar 自带顶层前缀,配方又写 subdir,两层一叠文件深一层,
license 校验和又炸。二选一去 subdir。两枚皱褶零绕过,全被
bitbake QA 如实拦下——构建系统的 QA 诚意白嫖了两道。

## 推 6(判据哲学)
构建集成最常见的自欺=止步"bitbake 跑通"。第 93 门:门禁
自调 bitbake(sstate 秒级)+第二台 QEMU 吃部署物起动+跑
musl hello+收尸 0。验证的是产品,不是构建系统自嗨。

## 推 7(体量账)
参考实现 yocto 76GB+六十枚补丁+它们的历史;我们:poky 上游净
克隆+4 文件层+2 装配脚本。构建系统的体量应该来自上游,
不是来自补丁。

## 推 8(链)
九十三门从此每轮都证明:yocto 出的活能跑真 libc。站 33 的
musl 判据在构建系统产品上复验——站点间的判据会自己接力。

## 推 9(下一站)
docker 收出货——从构建系统到交付形态的最后一跳。
Apache-2.0,结对从零造,结在中国造。
