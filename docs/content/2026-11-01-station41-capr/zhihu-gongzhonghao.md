# 站 41:能力框架,与一行被吞掉的函数调用

eshine-os 站 41 收口,也是既定序列的终站。机制面这一站做
的是 CAPR:每个进程从"全权裸奔"变成"能力上岗"。四位能力
位图(VFS/SPAWN/KILL/MM),创建即零能力,只有开机壳拿到
全权,fork 按位继承——而且系统里**不存在任何"加能力"的
路径**,唯一的写入口是自削(cap_drop)。self-inc-out 不需
要执法,由构造保证。执法是 fail-closed 的:fd 六门、
fork、kill、mmap 各设卡,缺能力即拒;配合 rlimit 自降
单向(第 4 个 fd 就 -EMFILE)和创建期随机 uuid(fork 得到
新身份,资源可以继承,身份不能)。这一套是参考实现五面——
表、fail-closed、self-inc-out、rlimit、uuid——的最小诚实
站内形。

但今天真正值得写的不是 CAPR,是把它做出来时埋进去的那颗
雷,和拆它的三个小时。

我往 sys_fork 里插两道新检查(CAP_SPAWN 和子进程数上限),
一次编辑把紧邻的 `rt_proc_create(NULL, &cp)` 整行吞掉了。
替换,而不是追加。cp 成了一个未初始化的野指针,下一行
就把 parent 的地址空间"拷贝"进它指向的任何地方——EL1
数据中止,然后掉进这个内核的静默驻车:一条 wfi 死循环。
没有故障行,没有崩溃打印,整个系统就安静地停在那里。壳
还挂着 state=RUN,所有服务器睡在 recv,谁也不会再醒。

法医弧上有三重伪象。第一重,尸检栈:我在壳的内核栈上读
出 sem_take_to、sys_write 的返回地址,以为是活调用链,
追了半天"是哪个信号量"——其实是几条 sys_puts 早前落串口
时留下的陈栈,那 272 字节帧是寄存器保存区,不是 C 帧链。
第二重,我给壳的状态和当前任务指针上了两个硬件 watchpoint:
零命中。任务从未阻塞、从未被切走——它一路跑进了驻车。第
三重,全量断点陷阱集(fd_fork、消息、信号量、子任务创建、
wait4)布好后继续跑,190 秒零停点——wedge 在 sys_fork 的
前 88 字节内,而 -O2 把一切内联,让"没停点"看起来像"没
执行"。

最后是 diff 一照面的事:`-rt_proc_create(NULL, &cp)`,
就一行,在减号侧赫然。判据先于结论——diff 应该是最先打开
的,我把它放在了最后。

还有一层机器背书的讽刺:构建里 **-Wall -Wextra 本来就在**,
吞行的那次构建,GCC 必然打了"cp 未初始化"的警告。警告打
了,没人读。freestanding 项目没有 -Werror 兜底,构建输出
就必须过眼——这是这次全费用里最便宜就能省掉的一课,却
没省。

另有一笔陈账顺手清了:壳 help 走查的头部步数从站 34 之后
就停在 93,六站的新门一直往清单尾部加,头部数字没人对过
账。同步纪律的"步数"字面也要对账,不只是新增行。

41 站齐了。从 28 站的 EL0 壳加 syscall 起步,到进程与地
址空间、三段消息 IPC、server 加 rootfs、signal 加 futex、
musl 直连、yocto 产品可靴,再到服务生态、busybox 双世界,
今天以能力框架收整——每一站都是 spec 先行、门禁两连绿、
三处同步、内容包同批。从零打造的第一季,到此收图。
