# 宿主第一次活在"被中断"里:GICv3 中断站,和五个连环套娃的 bug

> eshine-os 27.04 连载第 4 篇。代码 github.com/eshine-os/eshine-os,
> Apache-2.0,AI 结对(Claude/GLM-5.3)署名 git log 可查。

前三站打完,hypervisor 有一个尴尬的真相:宿主自己是 DAIF 全掩 + 轮询,
中断向量表的 IRQ 槽里躺着一行 WFI 停车。这一站把中断做成真的:宿主用
CNTHP 物理定时器每秒醒来一次记 tick;guest 有自己的虚拟定时器,sleep
两秒后在自己的向量表里醒来。听起来就是配几个寄存器的事。

代码写完,构建零警告,门禁跑起来——`ticks: 0`。再跑,还是 0。这一晚
后来变成一场五案连环的破案,每一案的凶手都是"我记错了",而且一个比
一个藏得深。

## 先说结局:全链路什么样

    eshine> tick            → ticks: 0 → 2 → 5        (宿主真中断,CNTHP 1s)
    vm0>   sleep            → sleeping...
                             → slept (vtimer irq)      (guest 自己的向量醒来)
    eshine> tick            → guest 退场后照常增长      (恢复面判据)

guest 的 `sleep` 走的链路值得单独念一遍:guest 武装 CNTV 两秒后 WFI →
WFI 被 HCR.TWI 陷阱到 EL2(不执行)→ 宿主自己 WFI 陪睡 → CNTV 到期,
物理 INTID 27 断进宿主 → 宿主把"vINTID 27、物理线同号、HW 映射"写进
ICH_LR0,然后对物理 27 **只降优先级不撤销** → 宿主醒来重进 guest →
guest 入场即被 ICV 投递虚拟中断,在自己的向量表里认领 → guest 一发
虚 EOI,硬件联动撤销宿主的物理线 → guest 醒后自查标志,打印 slept。
宿主与 guest 的中断面自此互不干扰——这就是虚拟化的含义本身。

门禁也从 17 步扩到 20 步,新增的三步分别钉死物理面(tick 严格递增)、
注入面(sleep→slept)、恢复面(guest 退场后 tick 仍增长)。第三步上线
当晚就抓出了第五个 bug,后面会讲。

## 案一:两个都诡异的写回行为

第一直觉的怀疑对象是 redistributor 的 SGI 帧偏移——但读回现象自相
矛盾:我往"组寄存器"写的值读回来粘住了,往"使能寄存器"写的值读回来
恒 0,像是写丢了。寄存器要么都收要么都不收,哪有只挑一个收的?

答案在 QEMU 源码里:`gicv3_internal.h` 明晃晃写着,GICv3 SGI 帧的
寄存器偏移是 **GICD 家族的镜像**——IGROUPR0 在 +0x80,ISENABLER0 在
+0x100,而 +0x104 是个未实现空洞:QEMU 对保留区 RAZ/WI,写被静默丢、
读回零。我凭记忆写的"紧凑布局"里,组配置恰好落在真使能位上(所以
"粘住"了——那本来就是使能寄存器),而真正的使能写进了空洞。两个
诡异行为,一个偏移幻觉全解释。

第一站 miniuart 的 FR 偏移教训重演:寄存器偏移抄手册,不抄记忆。只是
这次"手册"升级成了模拟器源码——后面会反复回到这一点。

## 案二:开了开关,但开的是另一个开关

偏移修对,ticks 还是 0。翻 QEMU 的投递路径源码(`arm_gicv3.c`),分发
条件里 GICD_CTLR 的三个组使能位是分别门控的:我写的 `GICD_CTLR=1`
只开了 Group 0。而 G1NS 中断走 bit1,还需要 ICC_IGRPEN1(这个我设了)。
更妙的是 Group 0 的中断需要 ICC_IGRPEN0——我从没设过。于是一个被
使能、在挂起的中断,因为落在"错误的组"里,cpuif 按源码里那行
`icc_igrpen[grp] == 0` 干脆**不产生任何信号**——不是 IRQ 也不是 FIQ,
连动静都没有。定时器这边 ISTATUS=1 拉着线,那边人间无事发生。

修法一行:开 EN_GRP1NS(bit1)。但当时我还不知道,这只解决五分之一。

## 案三:文档也会骗人,活探针不会

定时器到期的挂起位到底落哪个 INTID?我 dump 了 QEMU 的设备树,按槽
位序"推理"出 CNTHP=27,改了代码,还是 0。这里我犯的是更高级的错:
**拿文档反推运行时行为**。

最后上活探针:一次读回五个寄存器 + 当场认领(ICC_IAR1_EL1)。第二次
读,`pend` 的 bit 变成了 0x4000000——**bit 26**,和 CNTHP 到期时刻精确
相关。CNTHP=26,文档槽位序是我瞎指的。同一招再测 guest 的 CNTV:武装
半秒,刷屏的 `[unk-irq 0x1b]` 直接给了答案——0x1b=27。顺带那个刷屏
本身就是证据:电平触发的线被我误撤(EOD+DIR),立刻重挂起,认领风暴。
它反向证明了一个设计决策:vtimer 分支必须"只降优先级不撤销",把撤线
留给 guest 的虚 EOI 硬件联动。

接线以活体行为为准。三次探针(挂起位相关性、认领风暴、心跳打点)覆盖
了本站全部未知,比任何文档都诚实。

## 案四:一切都绿,就是不干活

这是当晚最魔幻的一段。门控链的每个输入我都验证过了:cpuif 拉高了 IRQ
线(QEMU trace 亲口说的)、核也看到了挂起(ISR_EL1 的 I 位=1)、DAIF 的
I 位清零、CurrentEL=2、HCR 我也写了……`-d int` 零条异常记录,gdb 在
向量入口蹲了五秒,断点零命中。**所有先决条件全绿,异常就是不发生。**

答案还是那句话:去读源码,别读记忆。QEMU 的 `target_el_table` 是一张
6 维查表,决定物理异常打到哪个 EL;在"无 EL3、rw=1"的这一列里,EL2
的物理 IRQ 只有在 hcr 输入为 1 时才路由回 EL2,否则表项是 EL1——
target 低于 current,异常**静默不取**。而 hcr 输入取自 HCR_EL2 的 IMO
位。我写的是 bit3,因为记忆里 IMO=bit3。QEMU 源码:`HCR_IMO = 1<<4`。
再翻参考实现的自有代码交叉验证:参考实现的 sysregs.h,`HCR_IMO_BIT =
(1UL << 4)`。bit4 才是真身。改一个数字,ticks: 0 → 2 → 5。

"所有灯都绿但机器不转"的时候,几乎总是有一个你以为验证过、其实验证
错了的输入——我的错误在于以为"我写了 IMO 位"等于"IMO 语义在生效"。

## 案五:门禁新判据当晚抓到的最后一个

还剩一个雷,藏在"退出 guest"这个动作里。20 步门禁的第 19 步要求
"guest 退场后宿主 tick 仍增长",它当场红了。而我手动测试时明明是活的
——区别在于手动测试里我读 tick 的时候 guest 只 WFI 过、没退出过。

真凶是 DAIF。异常进入 EL2 时硬件自动掩掉 I 位,而 guest 通过 HVC 退出
回宿主的那条路径上,没有任何人把 I 位解回来。于是宿主 shell 从此戴着
掩码永跑,tick 饿死。有趣的是为什么 guest 在场时 tick 反而活着:因为
那时活的 PSTATE 是 **guest 自己的**——guest 在自己的启动代码里解过
I 位。所以症状是"sleep 全流程能跑通、guest 一退出宿主就失聪",差一点
就把人引到 vgic 的方向去。心跳探针(每 5 tick 打一个点)把冻结时刻
钉在退场动作上,才收的网。修复:`vcpu_exit` 里补一句 `daifclr #2`。

这一案还有个注脚:中文 locale 下 make 报"错误",我 grep 'error' 判绿,
恒零——前两轮探针跑的都是陈旧二进制,白测。从这以后判绿只看退出码,
一律 LC_ALL=C。

## 收尾:三只红鲱鱼与一条方法论

红鲱鱼也值得点名,免得下一个人再追:GICR_CTLR 的 UWP 位是复位默认值
而且 RAZ/WI;GICR_WAKER 根本不门控 SGI 帧的写;RWP 在 QEMU 里没有
异步语义。三个都"看起来像凶手",都不冤。

本站沉淀出的方法论只有一句,但值回全部票价:**在模拟器之上开发,
模拟器源码就是地面真值**。本机 QEMU 8.2.2 与上游 v8.2.2 tag 逐文件
对齐(redist/dist/cpuif/virt/board),每个记忆里的位号,核得到源码就
核源码,核不到就活探针。五个 bug,五个都死于这句方法论,而我花在
第五个 bug 之前的时间,大部分是在学会这句话之前浪费的。
