# 站 47:跨 VM 服务面(内容包口径)

## 一句话

两个虚拟机怎么说话?一条宿主独管的共享窗+一个代际协议——
本站把参考实现的跨 VM 白描装进 eshine-os,取证路上撞出的却是
自家调度器的一条老规矩。

## 技术叙事(对外讲什么)

1. **safeshm 窗**:宿主在物理内存的空档刻 2MB,stage-2 双映给
   vm0 和 vm1;谁能映、映到哪,只有宿主说了算——安全面不在
   密码学,在配置权。协议是代际槽位:写方先备货后递增,消费方
   见到未消费的槽就读走并回执——任何时刻入场皆真。
2. **vm0 作设备后端**:RTOS 侧窗口是内核 EL1-only 映射,用户态
   经服务任务代访——设备驱动同律,零拷直写。
3. **本站最深的坑,分两层**:第一层是自己的站 28 家族——新块
   只加了内核页表半区,忘了 per-process 半区,壳的 demo 在
   SP_EL0 语境写窗,落进"静默驻车"向量槽,不打印不 panic,
   -d int 才定谳。第二层更妙:十连 gdb 取证(别名、双侧描述符、
   存档 PC、寄存器逐个)全部正确,交换就是不通——答案在自家
   调度器站 19D 的四行规则里:前台 VM 独享 CPU,后台 VM 零切片。
4. **依律重铸**:开机常驻静默生产者+消费者+host-owner 窗舞
   (消费后交还宿主,双 VM 并跑)——站在规则上设计,一次通过。

## 金句

- 仪器全绿而系统不工作时,下一个要审的是架构规则,不是仪器。
- 共享窗的安全不在密码学,在配置权唯一。
