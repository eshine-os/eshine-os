# 心跳、失联、恢复:一个健康监控面的最小实现

站 52,eshine-os 批次 A 的最后一站。前三站铺了日志契约(49)、日志
持久化(50)、服务治理(51)——这一站站在它们肩膀上。

## 健康面的最小内核

参考实现基准仓的 ham(health and monitoring)面有:实体、条件(state 型/
raise 型)、动作五型(命令/信号/消息队列/等待/日志)、心跳三态、
自愈守护。全搬到 QEMU 上的最小 RTOS?哪些是"必须有"?

站内答案:心跳实体+missed 条件+log 动作。每个实体声明期望拍距
(ham add hb1 100——100 tick=1 秒);内核任务每秒扫一遍,两倍周期
无声=MISSED;失联和恢复都走日志。就这些——但已经能回答最核心的
问题:"那个服务还活着吗"。

## 动作五型为什么只取 log 型

command(重启)、signal、bufqueue、waitfor——都是"失联之后做什么"
的策略。v0 的答案是:先让"失联"这个事实可靠地存在(入环、落盘、
可审计),策略层等真实消费者上门(站 33 纪律:按实测召唤,不臆测)。

## 三站合链

最满意的判据:[151] 门——ham 的 warn("ham hb1 missed")经站 49 的
elog 契约环,经站 50 的持久化落进 /var/log/slog,再由 busybox cat
读回。三个站在一个判据里合卷:说(契约)、记(持久)、看(健康)。
这不是三个功能的堆叠,是一条链的闭合。
