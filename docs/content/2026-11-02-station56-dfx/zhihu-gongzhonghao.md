# 观测面的收口:过滤、账本、老账

站 56,hypervisor 批次 B 的最后一站。三件小事,三种收口方式。

## 过滤:从倾倒到查询

vmtrail 是 16K 条的事件迹环——CPU、事件号、两个参数。之前只有
"最近 N 条"。现在 `vmtrail 16 cpu3` 只看 CPU3(vm0 次核专泵),
`vmtrail 16 cpu0` 只看 CPU0。取证从翻垃圾堆变成点菜。

为什么按 CPU 不按 VM?条目里存的是 CPU 号(4 字节),VM 要靠
拓扑反推——而我们的拓扑里 cpu1/2 就是 vm2、cpu3 就是 vm0 的次核,
只有 cpu0 是双客混载。按 CPU 过滤=按 VM 过滤的九成近似,不用动
16K 个条目的结构。诚实记档,不硬凑。

## 账本:抢占也记账了

每个 VM 的抢占数(两个扳机点:泵侧量子耗尽+异常侧帧转写)+量子
数,vmstat 两行。上一站记了量子账,这一站补上抢占账——治理面
要谈"谁抢了谁",先得有数。

## 老账:三笔"两仓同病"定谳

审计报告说参考实现和我们得同一种病的地方,这站清了三笔:
量子记账没有 cycle 补偿——granularity 就是量子本身,没有累积
损失路径,亚拍量子再议;CPU_ON 握手原子性——有界等待兜底,
丢拍降级不挂死,真板上 event register 语义要重审;宿主侧 FP
eager 保存——QEMU TCG 不是性能目标,RTOS 侧早就 lazy 了,
真板再议。三笔都记档,每笔带理由:不修的也要说清为什么不修。
