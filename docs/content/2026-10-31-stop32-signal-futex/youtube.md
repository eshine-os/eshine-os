# 站32 · YouTube 口播稿

**[开场]**
今天这一站,eshine-os 第三十二站,做 signal 和 futex——下一站
musl 进门之前,内核必须先备好的两张脸。futex 是 musl 所有锁
原语的底座,signal 是 POSIX 运行时的地基。九十门,两轮全绿。
但今天真正值得讲的,是排雷时撞上的那个 bug:它让一个子进程
说出了完全不属于它的话。

**[两张脸的形状]**
先说两张脸。futex,十六个桶,键是进程加虚拟地址:WAIT 一进来
先读用户字,值不等于期望值,立刻返回 EAGAIN,这叫值校验——
futex 快就快在无争用路径根本不进内核;值相等才挂队列睡,醒
来四路分诊:超时、被唤醒、被信号打断、还是值自己动了。WAKE
呢,按键把等待者从队列里摘出来,它连用户字都不读,纯队列
操作。signal 这边,投递点在系统调用出口:把被打断的二百七十
二字节整帧存起来,把 PC 改成 handler,把信号号塞进 x0——
handler 在目标进程自己的用户上下文里执行,不是内核替它跑;
handler 末尾调 rt_sigreturn,整帧还原,回到被打断的那条指令。

**[现场:子进程说胡话]**
然后是那个 bug。demo 链条:父进程 fork 子进程,子进程挂在
futex 上等,父进程杀它一个信号。冒烟结果:handler 确实跑了,
子进程退出码七也确实传回来了——但子进程接下来说的话是:
"futexdemo 超时,dt 等于四"——另一个函数的输出,还带着一个
刚刚现场测出来的 dt!handler 自己的话一句没说。

**[排查:证物是打印本身]**
纸上推演了四轮,寄存器、字符串池,全不对。最后把镜像反汇编
出来,对着 rodata 找每个字面量的地址——被打印的那两个指针,
恰好躺在 shell_line 函数序言的栈槽里:一个在 sp 加三百六十,
一个在 sp 加七百二。子进程打印的不是自己的字符串,是它错位
之后的栈窗口里恰好躺着的指针。也就是说:用户栈的 SP 错位了。

**[真身]**
为什么?我们的帧契约是二百七十二字节,elr、psr、x0 到 x30,
内核栈上整整齐齐——但 SP_EL0 根本不在这二百七十二字节里,
它驻在任务的 usp 字段,由异常进出的汇编代码在硬件域存还。
投递时我把帧存全了,却不知道 SP 有个影子在外面。handler 在
被打断的 SP 下面压了自己的栈帧;它的尾声本该把栈弹回去,但
sigreturn 的 eret 直接跳回了被打断的代码,handler 的 epilogue
永远不会执行——用户 SP 永久停在低了一个 handler 帧的位置,
后面的代码从错位的窗口读局部变量,三元判据读到的字符串指针,
就是隔壁槽里序言预存的别家字面量。修法一句话:投递时把
usp 一并存,sigreturn 时一并还。冒烟全绿。

**[教训]**
这一课入档成一条清单:凡做帧手术,必须清点帧之外的用户可见
态;凡手术必配对——存了什么,就要还什么。exec 那个站幸亏
本来就直写 usp,所以同样的病没发作过;这次是存了 A,忘了 A
的影子。
