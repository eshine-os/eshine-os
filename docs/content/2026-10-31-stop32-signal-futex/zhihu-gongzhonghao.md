# 一个 bug 让子进程说出别家函数的话:SP_EL0 不在帧里

(eshine-os 从零造 ARM64 Type-1 hypervisor+RTOS,站 32 记)

今天这一站做 signal+futex——下一站 musl 进门需要的两张内核脸。
futex 是 musl 所有锁原语的底座:WAIT(值校验+阻塞+四路分诊)/
WAKE(按 key 摘链,不读用户字);signal 是位图 pending+syscall
出口投递的帧手术:整帧存起来,改写 PC 到 handler,x0 塞信号号,
handler 在目标进程自己的用户上下文里跑,末尾 rt_sigreturn 恢复。
号面全部用真 Linux arm64 原号,90 门两轮全绿。

但今天值得写的是那个 bug——它完美演示了"帧手术"这类机器的
陷阱。

## 现场:handler 跑了,但子进程开始说胡话

demo 链条:父进程 fork 子进程,子进程挂在一个 futex 上等,
父进程 kill 它一个信号。期望:子进程的 futex 返回 -EINTR,
handler 打一行"信号到了",sigreturn 恢复现场,子进程打印
"-EINTR ok",退出码 7,父进程收尸。

冒烟结果:handler 确实跑了,"退出码 7"也确实收到了。但子
进程接下来说的话是:**"futexdemo: timeout r=-110 dt=4"——
另一个 demo 函数的输出,还带着一个新鲜的、刚刚测量出来的
dt=4!** 两个不同的字符串字面量、一次活的时间测量,从一段
根本不该执行它们的代码里冒了出来。

## 排查:打印内容本身就是证物

纸上推演了四轮:寄存器被 handler 打脏?不对——被打断点在
sys4 的 svc 返回处,它的序言/尾声对完整,epilogue 会从栈上
自愈。字符串池合并?地址互不重叠。最后把镜像反汇编出来,
对着 rodata 找每一个被打印字面量的地址,再看引用它们的代码:
**"futexdemo: timeout" 的指针恰好存在 shell_line 函数序言的
[sp+360] 槽里,"wake no-waiters" 的指针存在 [sp+720] 槽里。**

子进程打印的不是它自己的字符串,是它**错位后的栈窗口**里
恰好躺着的指针。也就是说:**用户栈的 SP 错位了。**

## 真身:SP_EL0 根本不在我保存的帧里

我们的 syscall 帧契约是 272 字节紧布局:elr、psr、x0-x30,
内核栈上整整齐齐。投递信号时我把这 272B 整帧存进进程的
sig_saved,改写 elr/x0,自认"现场已存全"。

但 **SP_EL0 不在这 272B 里**——它驻在任务的 t->usp 字段,
由 vec.S 在异常进出时存还(硬件域)。投递后 handler 在被打断
的 SP 下面压了它自己的栈帧,handler 末尾的 rt_sigreturn 用
eret 直接跳回了被打断的代码——**handler 自己的 epilogue(把
栈弹回去的那几条指令)永远不会执行**。于是用户 SP 永久停在
"低了一个 handler 帧"的位置,被打断的代码从错位的窗口读它的
局部变量,三元判据的字符串指针读到的是隔壁槽里序言预存的
别家字面量。

修法一行道理:投递时把 usp 一并存(sig_saved_usp),sigreturn
时一并还。冒烟全绿。

## 教训入档

1. **帧手术的完整性清单**:凡做帧手术(exec、signal 投递),
   必须清点 272B 帧之外的用户可见态——SP_EL0 在硬件域,
   不跟着帧走,就得手工跟对。
2. **存什么还什么**:exec_setup 幸亏本来就直写 usp 所以没炸;
   这次是"存了 A 忘了 A 的影子"。
3. **打印内容本身是证物**:"打出别家的字面+新鲜的 dt"这个
   组合直接指向错位读栈,而不是打印机抖动。反汇编+rodata
   地址比对三分钟定谳,四轮纸上推演不如一次直接看数据。
