# 从"能跑一个 guest"到"管得起两个 VM":我在 hypervisor 里踩的三个坑

> 本文是 eshine-os 27.04 连载第 2 篇。第 1 篇(26.10 EL2 骨架发布)见主页。
> 代码在 github.com/eshine-os/eshine-os,Apache-2.0,AI 结对(Claude/GLM-5.3)署名在 git log 里,欢迎围观。

上一站我们让 QEMU 里的 hypervisor 第一次跑通了 guest 往返:EL2 建 stage-2
页表,ERET 进 EL1,guest 用 HVC 打印 banner 后退出,宿主无损。但那是
"一个 guest 硬编码跑通"——离 hypervisor 该有的样子还差一层皮:**VM 得
成为对象,生命周期得被管理**。这一站补齐这层皮,顺手挖出三个值得单开
一章的坑。

## 这一站做了什么

目标一句话:**struct eshine_vm 从空壳变实体,shell 变小型 VM 管理器**。
命令面:

```
eshine> vmls            # 查看两槽状态
eshine> vmcreate 0      # 从预定义配置拉起 VM0
eshine> vmrun 0         # 进入 guest,回来时 VM_DEAD
eshine> vmkill 0        # 未跑先销毁
```

设计三决策(都值得展开,本文只点到):

1. **静态全量内嵌**:每槽自带完整的 per-VM stage-2 表(约 20KB)和 vcpu,
   没有分配器、没有堆。将来上分配器时只换 backing,接口不动。
2. **双镜像同源**:同一套 guest 源码,-DGUEST_ID=0/1 编出两个镜像,banner
   和提示符(vm0>/vm1>)不同,其余逐字节同构。
3. **隔离是映射层的物理事实**:两个 VM 的 RAM 窗口不重叠
   (VM0→PA 0x50000000,VM1→PA 0x51000000,各 16MB),同样的 IPA 0x40000000
   落进不同的物理页——VM0 就算把地址写烂也摸不到 VM1 的镜像。隔离不靠
   约定,靠页表。

验收判据固化成 14 步真绿门禁(空表→创建→双 VM 各自完整往返→全 DEAD→
宿主完整性复验→vmkill 拒绝路径),连续 4 次全过才提交。

## 坑一:把 20KB 的结构体放栈上,就是栈溢出

重构后 eshine_vm 内嵌了 stage-2 全套表,体积 ~20KB。而我宿主栈总共 16KB。
旧代码里 `struct eshine_vm vm` 还是栈局部变量——函数一开帧,栈直接砸穿
栈底,把下面内存里的 boot 期 stage-2 页表清了零。guest 首条取指就
Instruction Abort(ESR 0x82000005,L1 翻译错误),而宿主 shell 一切正常,
差点骗过"看起来没问题"。

教训一句话:**结构体含大数组,进栈前先算栈余量**。嵌入式没有 malloc
兜底,栈溢出的形态是"别人家数据被你改了",极其隐蔽。

## 坑二:描述符掩码砍低位,未对齐的表被指到别处

per-VM 的表集我起初只给第一张表(pgdl)做了 4KB 对齐,其余表紧挨着排。
而 stage-2 的表描述符是 `(addr & ~0xFFF) | 0x3`——**指针低 12 位被硬砍**。
没对齐的 l2_dev 表地址被砍回了 pgd 页首:gdb 一看,pgd[0] 指着 pgd 自己。

guest 挂在 L2 翻译错误(ESR 0x82000006)。第一站的静态表能工作,恰恰是
因为当时四张表**各自**标了 `aligned(4096)`——我抄自己旧代码时丢了这层
语义。修复:vm_space 每个成员独立 `aligned(4096)`,每表独占一页。

教训:**指针掩码类描述符(页表/描述符表)的对齐是正确性的一部分,
不是性能优化**。掩码即契约,契约即对齐。

## 坑三:ERET 之后,callee-saved 是 guest 的了

最隐蔽的一个。vcpu_run 返回后,vm_run 打印 VM id,输出却是
`vm1509949441: VM_DEAD`——1509949441 = 0x5A000001,正是 HVC 退出异常的 ESR 值。

为什么?C ABI 的 callee-saved(x19-x28)我确实在 vcpu_run 出口恢复过——
但那是 **ERET 之前**。ERET 进 guest 后,所有可覆盖寄存器全是 guest 的;
guest 退出经 EL2 异常链返回宿主时,寄存器里是 EL2 处理链的残留。第一站
没炸,只是因为调用方恰好只依赖 adrp 重载的字符串地址,没碰 callee-saved。

修复:出入口整块保存/恢复宿主现场(x19-x28 + sp + lr 进 host_ctx)。
教训:**硬件不承认你的调用约定,跨特权级往返后,"谁的寄存器"要靠
软件契约重述**。这也是下一站(完整 vCPU 上下文切换)的直接伏笔。

## 门禁工程:门禁自己也会撒谎

这站 14 步门禁的 flaky 折腾出两条纪律,写下来给同样做自动化验收的人:

1. **read_until 必须带"发送时刻"的位置下界**。不带下界,上一轮的旧输出
   会满足本轮判据——假阳性。
2. **每条命令的尾随 prompt 在发下一条前必须吃掉**。VM_DEAD 之后的
   prompt 在路上,与下一条 vmls 的判据竞争——假阴性。

测试器也是代码,陈旧匹配和竞态它一样会犯。
