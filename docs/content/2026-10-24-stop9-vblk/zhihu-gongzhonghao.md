## 先说结局

    [vm0] blk irq on
    vm0> dwrite
    blk wrote
    vm0> dread
    blk read: ESHINE-BLK-persist
    （vm0 exit 销毁 → vmcreate 0 重建）
    vm0> dread
    blk read: ESHINE-BLK-persist

写进去的东西,在一个 VM 的生命周期结束之后还在。这是 guest 第一次
拥有跨生命周期的"磁盘"。

## 设计哲学:virtqueue 的种子

这一站最值钱的决策是接口哲学:**内存即传输面,寄存器即门铃**。

- 512B 数据缓冲放在 **guest 自有 RAM**——它是唯一写者,不存在
  信任问题;宿主经 mem[] 静态映射翻译后**首次直访 guest 物理内存**
  (EL2 恒等映射,PA 即宿主可访地址)。
- MMIO 只承载门铃与状态:CMD/ADDR/STATUS/CAP/IMSC 五个字。
  大数据量走内存,控制流走陷阱——**不逐字陷阱搬运**,性能面
  与信任面同时成立。

这个切面就是 virtqueue 的种子:virtio 世界的 avail/used 环、
描述符链,本质都是"共享内存当传输面,寄存器写当门铃"。下一站
这颗种子会长成行业标准设备。

## 同步服务,异步完成

RAM 介质没有真实延迟,所以数据搬运在门铃陷阱内**当场完成**;
异步的只有完成中断:

    门铃陷阱(同步) → 搬运完成 → ris+imsc 置挂起
    → 泵调度到该 VM → 注 LR(vSPI 34) → ERET 抬虚拟中断线
    → guest ISR 读 STATUS 清挂起 → 回报 "blk wrote"

**请求→服务→完成→ISR**——设备模型完整生命周期的最小闭环。
virtio 的同构形态:下一站只是把"命令块"换成"描述符链"。

## 持久化=结构保证,不是代码逻辑

"销毁重建数据仍在"怎么保证的?不是我写了什么保持代码——是
**磁盘根本不在 vm_create 的复位路径上**。它是 vblk.c 里的静态
数组:vm_create 复位帧、复位 vuart、复位等待状态,但复位不到
模块级静态存储。**数据放对了地方,持久化就是结构保证**——
门禁 [25] 走全生命周期验证它。

这个哲学值得单独说:很多"特性"其实应该在结构层消化,而不是
在代码层维护。放对地方的东西不需要维护。

## 第二设备落地,欠账自然到期

第一个仿真设备(vuart)落地时,单设备直查无可厚非。第二个设备
一出现,表化欠账立即到期:

- vm_device 增 dev 字段,MMIO 窗口命中后按 VM_DEV_VUART /
  VM_DEV_VBLK 分发;表内未知设备类型=不变量破坏,直接 fault
  ——默认拒绝贯穿到设备层。
- 泵注入条件 uart||blk 并列;等待原因泛化为"设备中断等待"
  (非 TIMER 源共用再唤醒网)。
- LR 通道恰好用满 a57 四槽之三:LR0=vtimer(HW)/LR1=vuart/
  LR2=vblk。

## 首测一次全绿:无战况,但有时间线解释

本站手测五链(使能/写全链/读完整/销毁/重建持久化)**一次全过**,
门禁 28→31 步双绿(块设备三判据入册)。九站连载第一次没东西
可debug——读者当然要问:是这站简单吗?

不是。是账期到了:

- MMIO 分发框架(六)、ELR 两种面孔与 pc 代退休(六)、
  SRT 回填(六)
- LR 正形与泵注入纪律(八)、asm 访存器契约(八)
- 设备等待语义(六七八三代演化)、帧尾扩展纪律(五)

**前一站在怀疑论上花的每一分钟,都在这一站的红利里回收。**
第八站那个"位号名实分离"的坑,如果当时用"能跑就行"糊过去,
这一站的完成中断会以完全相同的方式静默失败。怀疑论的复利,
在设备站开始兑付。
