# 知乎/公众号长文:崩溃的仁政——站 46 取证链手记

## 标题候选

- 《一个野指针,凭什么全 VM 陪葬?》
- 《死前留遗照:给用户进程的崩溃装取证链》

## 正文骨架

### 一、连坐制度

站 29 定契约时留了一条边:EL0 野访(没有 VMA 覆盖的地址)=
全系统 panic。当时的理由诚实——v0 不知道谁在野访,分不清
"用户崩了"和"内核坏了"。但站 38 之后信号默认动作已经走进程
exit 链了,硬件异常还在全灭:同一个"用户进程该死"的语义,
两条路径,一个连坐一个仁政。本站翻案。

### 二、死者本人语境

野访者现在走 sys_exit 同链:fd 清、线程群扫、ZOMBIE、父收尸。
code=139(128+11,SIGSEGV 面)——与信号终局同一台机器,零新
死亡流程。内核自己的异常(EL1)仍然全驻车:保守面留对了地方。

### 三、遗照:crash 环

死前留档:tick、pid、任务名、esr/elr/far 硬件三元、退出码、
x0-x5+x29 寄存器面、用户 x29 帧链前 4 帧。两槽环形,新记挤旧记。
ELF 核文件落盘在我们架构里不可为(ramfs 是只读 rodata 服务器),
内存记录+shell 倾倒就是诚实形——差异记档,不冒充。

### 四、走用户栈的三个门

帧链要从死者的栈上走,坏栈随时可能把取证变成 EL1 二次事故。
三个门:窗门(指针和返回地址都不许出用户窗)、映射门(每次
读之前查 PTE present)、单调门(栈向高地址长,环即断)。
取证工具的第一美德是不制造新事故。

### 五、两枚雷

首版 0 帧:-O2 用户码默认不链帧指针,x29 是残值——加了 x29
转储诊断才发现(仪器先于判据;顺带自曝一次十六进制心算错误)。
第二枚想走捷径:函数级 optimize 属性局部开链,结果污染整个
编译单元、凭空炸出 strlen。终修是 demo 手工挂一帧 {x29,x30}
当法医夹具:walk 由野读点证活,真链用户构建(-fno-omit)
接上同一机器就是全链。
