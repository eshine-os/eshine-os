# 调试十八天不如取证两小时:一个"tick 冻结"下面压着的三个真身

(eshine-os 从零造 ARM64 Type-1 hypervisor+RTOS,站 28 收口记)

做系统软件最怕的不是 bug 难,是**好几个 bug 长了同一张脸**。我们
站 28 把 shell 升格成 EL0 用户态后,门禁 [24+] 开始"游走失败":
有时睡门超时,有时 PI 演示冻死,有时二次引导全静。症状统一到
一句话——"回复在而 tick 冻结"(你敲键盘它还活着,但内部时钟死了)。

WIP 检查点时我把它挂账成"vtimer 陈疾"。今天收口,猎捕器+全环
决策日志+差分采样三件套轮番上,真相是**三个互相独立的缺陷共用
这一个症状**:

## 真身一:弹栈弹错了库(客户机侧)

EL0 的 shell 阻塞时,内核要把 CPU 交给 EL1h 的任务。这段切换
汇编要跨两个栈指针"库"(SP_EL0/SP_EL1),旧代码弹栈的推进记在了
错误的库里——等 eret 返回 EL1h,栈指针**仍是弹栈前的旧顶**。
每切换一轮,栈净漏 272 字节。idle 任务的 8KB 引导栈 20 个周期后
踩穿旁边的软定时器表,tick 中断一解引用野指针就 panic。

定位手段很笨但有效:**剥掉 shell 交互,gdb 三次采样 idle 的栈指针
——纹丝不动**。泄漏只随"阻塞-唤醒"周期走,嫌疑面瞬间从整个调度
器缩到一条切换路径。

## 真身二:宿主的"无主收尸"

ARM 的虚拟定时器中断(27)在宿主自己的时间片里到点时,宿主的
处理逻辑有三分支:泊着睡的唤醒它/在途的记账它/都不是就当"无主
挂起"收尸。第四种情况漏了:**可运行任务的定时器恰好落在宿主片
隙**——sweep 只认睡着的,inflight 只认在途的,双不中就被当无主:
物理中断被认领后永远"active"且不注入,线恒高、再投递被挡,
滴答永死。协作式内核还装没看见继续跑,直到某个依赖 tick 的
自旋演示把尸体撞上判据面——**死点比可见冻结早 40 秒**。

修完第一版当晚就被打脸:`(id<<4)|vi` 这个打包值对 vm0 的
vcpu0 来说等于 0,和"未初始化"哨兵撞车,修复代码把唯一的受害者
拒之门外。修法必配最小复现器,当晚抓回。

## 真身三:复用帧带了前世记忆

VM 销毁重建时,复位清单漏了后来新增的九个字段——包括
SCTLR(MMU 开关)。新客户带着前世"MMU 已开"入场,引导代码
清 .bss 时把**正在使用的页表**抹了,取向量地址即炸出无限
自陷风暴,单轮 -d int 日志 230MB。字段清单纪律:"struct 每加
字段,复位清单同步加"——这句话用七站绿灯换来的,值。

## 结语

81 门连续两轮全绿收口。三个真身,两种修法自雷,一条教训:
**症状同名 ≠ 根因同源;判据先于结论,仪器先于判据。**
