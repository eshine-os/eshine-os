# 站28 收口 · YouTube 口播稿

**[开场]**
"回复在而 tick 冻结"——这八个字困扰了我们整整一个检查点。键盘
敲下去 shell 还会回你,但内部时钟已经死了。今天这一站,我们不
只修好它,还把它的真身挖了个底朝天。欢迎回到 eshine-os,
从零造 ARM64 Type-1 hypervisor+RTOS,第二十八站收口。

**[本站正题]**
先说正题。站 28 把 vm0 的 shell 从 EL1 内核任务升格成 EL0 用户
任务:两区式 stage-1 页表——内核区用户区分开,EL1-only 的块和
EL0+EL1 的块用不同的 AP 编码;EL0 异常蹦床——SVC、IRQ、fault
三个入口,各自的栈库切换不变量;还有 Linux arm64 标准的 syscall
ABI,号放 x8,参数 x0 到 x5,返回负 errno。read 是 63,write 是
64,getpid 是 172——同一个 ABI,以后 musl 就能直接进来。

**[挂账与三重真相]**
WIP 检查点的时候,门禁 24 号以后开始玄学:睡门超时、PI 演示冻
死、二次引导装死。当时挂账"vtimer 陈疾"。今天取证,真相是:
**三个互相独立的缺陷,共用同一个症状**。

第一个,弹栈弹错库。EL0 语境切 EL1h 任务,栈指针有两个库,
弹栈的推进记错了库——每切换一轮净漏 272 字节。idle 任务的
8KB 引导栈,二十个周期踩穿旁边的软定时器表,tick 中断一解
引用野指针,当场崩溃。定位它用了个笨办法:剥掉 shell 交互,
三次采样栈指针,纹丝不动——泄漏只随阻塞-唤醒周期走。

第二个,宿主的"无主收尸"。定时器中断恰好在宿主自己的时间片
里到点,处理逻辑有三分支:睡着的唤醒、在途的记账、都不是就
收尸。漏了第四类:可运行任务的活火。被当无主收尸——物理中断
认领后永远 active、零注入,滴答就永远死了。而协作式内核还
装没事继续跑,死点比可见冻结早四十秒。

第三个,帧复用带前世记忆。VM 销毁重建,复位清单漏了后来新增
的九个字段,包括 MMU 开关 SCTLR。新客户带着"MMU 已开"入场,
引导代码清 bss 的时候把正在使用的页表抹了——取向量地址就炸,
无限自陷,单轮异常日志两百三十兆。

**[修法自雷]**
修复过程自己还踩了两个雷:一个补偏差了 16 字节,寄存器全串位;
一个是 ID 打包值对 vcpu0 来说等于零,和"未初始化"撞车,修复
代码把唯一的受害者拒之门外。所以我们的纪律是:新修必配最小
复现器,当晚抓回。

**[判据与收口]**
81 门——新增 utest 门,验 EL0 syscall 全链——连续两轮全绿。
分层回归:看门狗三十轮全过,全任务混合四十轮全过,冻结复现
六轮全过。修复前分别是两轮死、随机死、首轮死。
