# 80 行 JSON 解析器,换来一套服务治理面

站 51:给 eshine-os 的 RTOS 补参考实现基准仓的 driver_manager 机制。

## 要解决的问题

开机链原来是写死的:inittab 逐行跑,respawn 靠壳轮询。参考实现的
driver_manager 用一份 JSON 清单描述所有服务:谁先谁后(order)、
起来没有(pre_wait 就绪门)、挂了怎么办(recover+重启上限)。这是
"服务治理"和"启动脚本"的分界线。

## 80 行解析器的底气

为一份机器自己生成的清单引入 cJSON?不值得。schema 约束:清单由
仓内配方生成,永远只有平对象、字符串、整数、布尔,没有嵌套,没有
转义。解析器只认这个方言——js_key 按键取值,jsv_str/jsv_int 读值,
90 行结束战斗。约束换来简单,简单换来可审计。

## 治理链

三个演示服务把全部机制跑通:marker(先跑,产标记文件)、gated(就绪
门等着 marker 的文件出现才起步)、beater(respawn 模式,退出即重启,
两次后达到上限,giving up 收场)。开机自动跑一遍;svcdemo 命令
交互复跑——门禁判据锚在复跑上,boot 窗全 buf 审计兜底。

## 一个雷

行走器入口契约:js_key 要同时吃"整个文档"和"单个服务对象"两种
输入,前者带 '{' 开头——首版漏跳这个字符,manifest parse failed
一发入魂。解析器的入口形态和调用形态必须成对想清。
