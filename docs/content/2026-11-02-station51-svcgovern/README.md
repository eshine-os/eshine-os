# 站 51:服务治理面(内容包口径)

## 一句话

服务怎么起、按什么顺序起、起了没有、挂了怎么办——从写死的启动
序列,变成一份 JSON 清单说了算:有序拉起、就绪门检查、退出监控、
重启有上限。

## 技术叙事

1. **清单即配置**:服务定义(名字/路径/模式/就绪门/重启上限)进
   /etc/services.json——治理逻辑与被治对象分离。
2. **自研最小 JSON 行走器**:schema 约束的解析器(平对象、无嵌套、
   仓内配方生成)——80 行换零依赖,不为一个清单引入一个库。
3. **就绪门**:后一个服务等前一个的产物文件出现才起步——顺序不只
   是"先发起",是"确认过"。

## 金句

- 治理不是把服务管起来,是把"谁先谁后、挂了怎么办"写成数据。
- 解析器小到只认自己的清单,就不需要防御全世界的 JSON。

## 数字

- 门禁 145→148;冒烟 18/18;JSON 行走器 ~90 行;就绪门 100 拍上界。
