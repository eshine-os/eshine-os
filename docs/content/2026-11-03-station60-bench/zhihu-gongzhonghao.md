# 第一个性能站:唤醒延迟直方图,和一场号面事故

站 60,批次 D 首站:benchmark 延迟基线。

## 基线长什么样

vm0 里跑 cyclictest 形的 demo:一个任务每 10ms 唤醒一次,量
"实际唤醒-名义周期"的超额,200 环入 1ms 桶。结果:

- 0-6ms:基本为零
- 9-10ms:149 环(主簇)
- >10ms:50 环(尾)
- 单发 5-6ms:1 环

主簇 9-10ms 是什么?**恰一拍超睡**。我们的调度器是 100Hz tick:
nanosleep 的 POSIX"至少睡够"语义,在 tick 量子上要 ceil+1 个拍界
才保证——醒来时刻 = 一拍减去拍内相位(实测相位锁定 ~30µs)。25%
的尾部是相位游走:环路周期和拍周期差拍累积,偶尔跨拍界多吃一拍。

0-1ms 桶恒零,同样重要:tick 调度器没有亚拍唤醒这件事,直方图
替我们说清楚了——hrtimer 是后弧的账,不假装有。

## 号面事故

首版我给 nanosleep 配了 syscall 号 35——冒烟直方图全 0-1ms 桶,
demo 返回 rc=-1、errno=38(ENOSYS)。三个信号同时指向一个事实:
这个号根本没人接。

35 是哪来的?x86_64 的 nanosleep。aarch64 走 asm-generic 编号,
真号是 101。这是站 42 就立过的纪律的重犯:号面必读 musl 头,
不靠记忆。中间还走过弯路:想用反汇编数引用定谳,结果 objdump
的符号注记根本不可靠(sendto 计数 0 而它明明活着)——最后是
直读 musl 安装头一行定案。

## 基线的纪律

数字是基线,不是门:门禁只断言直方图形状(主簇桶非空)和上界
(max 不超 3 拍),数值落盘 docs/benchmark/,留给后续站(真板、
中断接管、优先级面)重跑对照。主簇右移=调度退化红旗,那是后面
每站都要看一眼的趋势面。
