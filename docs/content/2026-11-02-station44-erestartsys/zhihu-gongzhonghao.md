# 知乎/公众号长文:信号打断系统调用之后——站 44 可重启语义手记

## 标题候选

- 《为什么你写的 retry 循环本可以在内核里消失》
- 《ERESTARTSYS:内核替用户撒的一个善意的谎》

## 正文骨架

### 一、老契约的账

站 32 定契约时:信号打断 futex 等待,直接返 -EINTR。简单,诚实,
但把成本转嫁给了用户——每个调用方都要写 `while (1) { r = futex();
if (r == -EINTR) continue; break; }`。内核明明知道"其实什么都没
发生",却让一万个用户各自翻译这句话。站 42 审计把 ERESTARTSYS 记
在"裁剪"栏,本站翻案兑现。

### 二、Linux 的答案

-512(ERESTARTSYS)是不越 ABI 的内核内部值:阻塞原语被信号打断
时返回它,分发器看到就做两件小事——**elr 减 4**(异常入口的
ELR 指向 svc 的下一条指令,减 4 就是重新取指 svc)、**x0 槽不写**
(正常路径 x0 槽是返回值,重启路径保住入参,svc 重执行=同参再入)。
有 handler:出口投递整帧存档,handler 跑完 rt_sigreturn 恢复整帧,
eret 落在回拨后的 elr 上——系统调用装作无事发生。无 handler:
默认动作终局退出,回拨无害。

### 三、两个机制的咬合

本站最漂亮的发现:信号投递(站 32)本来就是"整帧 272B 存档+
改写 elr/x0 进 handler";重启手术只要赶在存档前落笔,零新机器。
帧手术纪律"动什么还什么"在这里变成"假装什么都没动"。

### 四、判据埋在 handler 里

怎么证明重启真的发生了?让 handler 自己把 futex 字戳成 1——
重启再入的入口值校验会立刻 -EAGAIN。这一个判据同时证明两件事:
elr 没回拨的话,执行的会是 svc 后面的错窗垃圾;x0 没保入参
的话,-512 当地址早就野访 panic。如果哪天重启破了,旧脸 -4
会落 FAIL 行,门红自抓——判据自带反面雷。

### 五、不重启的与重启的一样重要

sigsuspend 恒返 -EINTR(POSIX 特例,Linux 同律);poll 家族
never-restart;我们的 sem/msg 打断本就被 take 环吸收重挂
(醒后出口投递,站 32 既有契约),不生产重启。语义表是完整的,
不是"全都重启"的一刀切。
