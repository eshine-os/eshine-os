# 坏 guest 杀不死 hypervisor:vCPU 上下文切换与一个 79 发陷阱才爆的栈泄漏

> eshine-os 27.04 连载第 3 篇。代码 github.com/eshine-os/eshine-os,
> Apache-2.0,AI 结对(Claude/GLM-5.3)署名 git log 可查。

上一站结尾我留了个尾巴:guest 的 x19-x28 跨超调用存活,靠的是"EL2
处理程序编译后恰好不碰 callee-saved"——一个编译器巧合。这一站把巧合
变成契约:guest 全量现场进陷阱帧,顺手做出三件更帅的事。

## 一晚三件事

**① 陷阱帧**。向量表的 lower-EL sync 槽不再直接跳进 C,而是一段 asm 桩:
把 guest 的 x0-x30 + SP_EL1 + ELR + SPSR 全量存进 vcpu 结构,再调处理
程序。x0-x30 里 x18-x28 属于 guest,连保存动作本身都不能借它们当
scratch——先在异常栈上停住 x0,才腾得出手。从此 **EL2 用什么寄存器与
guest 无关**。

**② yield 断点续跑**。新超调用 HVC #2:guest 主动让出,VM 转 PAUSED;
再 `vmrun`,guest 从断点**原地继续**——hvc_yield() 像普通函数调用一样
返回,后续代码照跑。Week-1 就画进状态机的 PAUSED 状态,这天第一次真正
被用上。状态机零新增转换:设计红利兑现的感觉。

**③ fault 隔离**。guest 读一个未映射地址:VM 死,宿主活。诊断行
`fault: ESR/FAR/pc/sp/x0-x3` 读的是陷阱帧——所以能看到野指针的**原值**:

```
vm1> fault
fault: ESR=0x93c08006 FAR=0x30000000 pc=0x40000354 sp=0x40002700
       x0=0x30000000 ...
vm1: faulted -> VM_DEAD
eshine> echo ALIVE
ALIVE
```

而宿主自己的异常仍然是 panic + WFI——**边界反转**:guest 的崩溃是
数据,宿主的崩溃才是事故。

## 坑一:noreturn 反杀

`vcpu_enter_guest` 被我标了 `__attribute__((noreturn))`。但 guest 退出时
它**真的会返回**(还宿主现场后 ret 回调用点)。GCC 信了 noreturn,在调用
之后不生成任何代码——第一次 exit 落进死区,静默挂死。

noreturn 属于 eret 出去的 `trap_resume`,不属于会还栈返回的进入口。
属性的语义边界,编译器比你认真。

## 坑二:每陷阱净泄漏 110 字节,79 发后碾穿栈底

本轮最肥的 bug,值得完整讲。

**现象**:门禁在"VM0 完整跑完后跑 VM1"时,VM1 的 banner 打到第 32 个
字符突然死于全零现场,宿主也连带崩。手工单跑 VM1 却完好。

**机制**:trap_resume 是 eret 出去的——**没有任何代码把 SP_EL2 还回去**。
每次 HVC:异常入口用 SP_EL2、处理链压帧、eret 走人,SP_EL2 停在低位。
下一次陷阱从这里继续往下压。每次净泄 ~110B,第 79 发陷阱(VM0 约 52 发
+ VM1 第 37 字符)恰好碾穿 4KB 异常栈底——而 `cur_vcpu` 全局变量就在
栈底下方 16 字节。指针被踩烂,下一发陷阱从烂指针读出全零"帧",
guest 被恢复成 PC=0、寄存器全零,当场指令中止;退出路径又用同一结构的
全零 host_ctx 还宿主,宿主 ret 到 0。

**为什么上一站没炸**:第二站的门禁全流程约 84 发陷阱 × ~32B 泄漏 ≈
2.7KB,没越过 4KB。**不是没有 bug,是余量还没用完。**

**修复**:el1_trap 入口把 SP_EL2 归位到栈顶,再调 C。异常入口归一化
自己的栈,处理链允许弃帧。教训写进 ARCHITECTURE.md:**任何"不退栈"的
eret 出口路径,栈归位必须发生在入口,不能指望出口。**

## 坑三:GCC 把我的测试判据优化没了

selftest 命令:0-99 求和,跨 100 次 HVC 存活,校验 4950。写完一反汇编——
循环体里**没有累加指令**。GCC -O2 把等差数列求和折叠成常量 4950,判据
成了空转。

修法是经典的一行:循环里插 `__asm__ volatile("" : "+r"(sum));`。
空指令,但挡住常量折叠,sum 被迫真活在寄存器里。再反汇编:
`add x30, x30, x19` 紧挨着 `hvc #0`——**求和活在 x30、计数器活在 x19,
两个都是帧保存的寄存器,跨 100 次陷阱**。这才配叫寄存器完整性测试。

三连坑各不相同,方法论却是同一个:**门禁一红就追到底,反汇编/gdb 拿
运行时铁证,不靠推理收敛**。

## 收尾:与参考实现对了一遍表

这站还做了件工程纪律上的事:扫描参考实现(只看结构不抄
代码)的 trap 形态做对齐。结论:asm 桩 + C 处理器 + 帧加载续跑,形态
同构;寄存器组信息等价(它把 x30 叫 lr)。三条真差异(帧归属层级、
退出原因显式枚举 vs 四层隐式拼合、fault 策略粒度)登记进偏离簿,
每条都标了参考源——**clean-room 不是闭眼,是睁眼记账**。
