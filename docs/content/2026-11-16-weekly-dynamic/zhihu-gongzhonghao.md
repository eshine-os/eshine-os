# 开源第一周：把私仓变成"敢让人看"的仓库

> eshine-os 开源周记 —— 公开发布这一周，一行内核代码都没写，全花在了"配得上公开"上。

## 先看结果

eshine-os 开源公开这周完成了三件套：

- **主仓**：https://github.com/eshine-os/eshine-os（Apache-2.0）
- **镜像**：https://gitee.com/eshine-os/eshine-os（国内可达）
- **官网**：https://www.eshine-os.org（kernel.org 风格，架构图按 ISO 26262 ASIL 和 ISO/SAE 21434 CAL 双轴分级，附路线图）

当前状态一句话：**ARM64 Type-1 hypervisor + 从零写的 RTOS 管理域 + 真 Linux 6.6 客户机**，
68 个开发站、183 个可重放验证门、公开史近 240 个提交、自研约 2.5 万行 C/汇编。
mainline 走 27.04-dev，stable 是 v26.10。

但今天这篇想讲的不是功能，是**发布工程**——开源这一周，我一行内核代码都没写，
全部时间花在把"能跑的私仓"变成"敢让人看的公仓"。五件事，件件都是教训。

## 第一件：合规清洗——历史里的每一个字节都要过堂

私有仓变公开仓，最大的坑不是现在的代码，是**历史**。两百多个提交里，早期的
commit message、文档、脚本会带着：公司内部仓的引用、私有管线的名字、
内部工具的标识。这些不是"删掉现在的"就完事——git 历史里全在。

这周的清洗做了五趟全历史改写，目标只有一个：**任何人在任何历史版本里
看到的，都是中性、可公开的表述**。改写不是拍脑袋，改完做了全历史关键词
复扫，逐字确认 CLEAN。

工程上的体感：改写历史最容易翻车的不是技术（filter-branch 熟练工），
是**判据**——什么叫"需要中性化"？答案要写成清单：商标、参考仓标识、
私有通道名、绝对路径。清单先行，逐项扫，而不是"感觉差不多了"。

## 第二件：真实署名——AI 结对不装人

这个项目的代码是人和 AI 结对写的（Claude Code、GLM-5.3 等，git log 可查）。
公开之前必须回答一个问题：**提交里的 AI 参与怎么记才诚实？**

这周落地了一套真实语义的 trailer 规范：

```
Model: glm-5.3                        ← 主模型
Assisted-by: Claude Code              ← 实际参与的其它模型
Reviewed-by: <评审者>                 ← 只有真评审过才写
Signed-off-by: Julian Chu             ← DCO，唯一末行
```

关键设计：**机器背书**。一个 validator 脚本同时挂在 git hook 和 CI 上，
旧式的"统一四行模板"在新提交里直接拒绝。历史提交里的统一模板怎么办？
专门的 ATTRIBUTION 文档坦白说明：那是模板，不是逐条参与证明。

诚实署名这件事，说到底是一句话：**AI 参与是事实，就按事实记录**。装人
是对未来贡献者的欺骗。

## 第三件：环境隔离——"克隆即构建"

私有仓有个隐形特权：构建脚本里写死了本机的路径、本机装好的工具。
公开仓库不能这样——别人克隆下来，`make` 应该就能跑。

这周的改造：**单工作根 `ESHINE_WORK`**。所有构建产物、第三方源码、
下载缓存都进这一个根目录，仓库树本身宿主无关。然后加了一个
check-host-independence 脚本，扫描 tracked + untracked 文件里的
宿主路径泄漏，连 `make -n` 的输出都查。

## 第四件：容器化——`--network none` 里跑 QEMU

隔离的终点站是容器：钉版容器镜像里，从构建到 QEMU 开机到交互 shell，
全程 `--network none`——**容器里没有网**，能跑起来才证明没有隐式依赖
在偷偷下载。

周一早上还收到一个现场报告：某台宿主机上 curl 解析失败但 wget 能活
（glibc 解析器路径差异）。修法两层：下载函数 curl→wget 回落；容器
run 之前先在宿主侧完成工作根 bootstrap（网在宿主侧，工作根反正要
挂载进容器）。现场报告→定位→修复→容器内端到端验证，一个上午闭环。

## 第五件：诚实边界——把没修完的挂在门口

这是我最在意的一件。开源发布最容易犯的错：README 写成宣传页。

eshine-os 的选择是把 KNOWN-ISSUES.md 挂在门口，五条开放缺陷白纸黑字：

1. 双核 demo 门 [37]/[38] 有深层污染族（守卫和取证已在，根因没收敛）；
2. 交互 shell 空格洪水残面（约 1/3 运行出现，绊线已埋，未自首）；
3. 全量 183 门对宿主负载敏感，两连真绿未达成；
4. 仅 QEMU virt 验证，真板未启动；
5. 安全边界（PAN/KASLR/形式化/模糊测试）是路线图目标，不是完成态。

**发布不是庆功，是签合同**——跟未来每一个贡献者签：以上是已知债务，
别踩坑，欢迎来收。

## 彩蛋：今天顺手修的一个小 bug

发布第一天就收到报告：官网在手机上，`mainline:` 那张发布表超出了屏幕。

根因有点好笑：官网样式从 kernel.org 的开源主题移植而来，桌面端没问题；
移动端的 848px 媒体查询移植时**漏掉了一条规则**——`#releases` 表的
滚动容器（`display:block; overflow-x:auto`）。kernel.org 自己的手机版
靠这条规则让五列表格在窄屏里横向滚动；我们没有这条，表格就按内容
最小宽度硬撑，戳出屏幕 70px。

修复就是把上游规则补回去（顺手把 CSS 升到 v7 做缓存穿透）。验证很较真：
DOM 探针测文档滚动宽（修复前 445px、修复后 360px @375px 视口），
部署后截图与本地验证版**逐字节一致**，前后像素差分确认变化只发生在
那三行表格的越界条带。

教训一句话：**移植别人的主题，媒体查询要逐条对上游，断点内每个区块
都要点名核对**——漏一条，手机上就是事故。

## 下周计划（缺陷预算优先）

这个项目有条铁律：**有 P0 级已知缺陷时，不开新功能站**。所以下周：

1. [37]/[38] 双核污染族 root-b/root-c 攻坚（root-a 已修，守卫已带全息取证）；
2. 收敛后 183 门两连真绿（安静窗）；
3. bsh 空格洪水自首；
4. 然后才是站 69 候选：EL2 边界模糊测试 / sub-tick hrtimer / SMMU·GIC-ITS 真板预习。

每周一会打周标签（`26.11-3w` 已打，锚定本周最早提交）并发一份周动态。
