# 站31 · YouTube 口播稿

**[开场]**
打开一个文件,读它,关掉它——这个动作你每天做几百次。
但"打开"到底打开了什么?Linux 说:fd 是个整数。微内核说:
不,fd 是一条通往服务器的通道。今天这一站,eshine-os 第三十一
站,把 fd 的真身——通道三元组——落了码,八十八门两轮全绿。

**[open 的解剖]**
先解剖一次 open。用户进程调 fdopen,斜杠 etc 斜杠 motd。内核
查命名表,找到 ramfs 服务器的通道,先建一条连接;然后把路径
打进一条六十四字节的消息,用上一站的三段消息发给服务器。
服务器在它开机解析好的归档索引里找到文件,立一个"每打开控制
块"——哪个文件、读到哪了——把编号回执回来。客户端把这个
连接号加控制块号存进 fd 表。fd 到此才诞生:它不是"打开的
文件",是"通往服务器的会话句柄"。之后的 read、write、close,
全部是消息往返,没有一行直接碰文件。

**[rootfs 是真的 cpio]**
根文件系统我们用了真格式:cpio 的 newc 磁带格式。一百一十字节
的头,六字节魔数,十三个域、每域八个十六进制字符,名字补四
对齐,数据补四对齐,最后 TRAILER 三个感叹号收卷。构建期一个
四十行的 Python 工具把目录树打进归档,汇编内嵌进内核只读区。
关键在最后一件事:归档在内核区,用户窗根本看不见——文件的
内容只能经消息拿到。这就是 fd 等于通道三元组的安全本义:文件
服务是一个可审计、可替换的服务器,不是内核里的隐藏特权面。

**[POCB 的双侧镜像]**
最有意思的一课来自 fork。子进程继承 fd 表,父子共享同一个
"每打开控制块"。谁管引用计数?答案必须双侧镜像:客户端的
连接引用加一,同时给服务器发一条 DUP 消息,让服务器侧的
控制块引用也加一。只做单侧会怎样?父进程先退出,把控制块
释放了;子进程还攥着这个 fd,而服务器把同一个编号发给了下
一个 open——两家的文件位置开始互相串写,而且不报错。引用
计数这种东西,不对称就是悬空。exit 的镜像面:死亡关流,逐
fd CLOSE,一层层对称收口。

是存量,git stash 掉改动跑了一次 make——然后 pop 回来,忘了

二进制调试了十五分钟,最后用 ps 直证法定谳。教训入档:任何
stash、checkout 这类环境操作之后,重建,再判断。另一颗雷
