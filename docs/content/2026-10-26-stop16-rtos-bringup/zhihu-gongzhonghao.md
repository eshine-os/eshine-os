# 我的 Hypervisor 长出了真 RTOS——顺便抓了五个藏了十五站的幽灵

> eshine-os 从零系列 · 第十六站。VM0 从 185 行裸机循环升格为任务
> 内核:位图抢占、100Hz tick、中断驱动 shell。然后,十五站攒下的
> 隐患在一天内全部爆雷。

## 先看结果

```
[vm0] eshine-rtos 27.04-dev @EL1 via stage-2 (vuart @trap)
[vm0] rtos: up 32-prio bitmap, tick 100Hz
[vm0] rtos> ps
  shell     prio 5   RUN
  heartbeat prio 10  SLEEP
  idle      prio 31  READY
[vm0] fp OK: 500000500000
[vm2] [    0.000000] Booting Linux on physical CPU 0
[vm0] rtos: alive tick=4450
[vm2] [    0.000000] rcu: srcu_init: ...
[vm0] rtos: alive tick=4500
```

RTOS 的心跳行夹在 Linux 引导流中间——串行日志的顺序就是证据:
两个客真的在同一颗 EL2 上并发。`fp OK` 那行是 SIMD 帧的验收:
fp 任务用 Q 寄存器手写汇编跑一百万次 double 加法,闭式校验
500000500000 一分不差——编译器被仓规禁用浮点
(-mgeneral-regs-only),这个结果只可能来自真实寄存器;计算期间
任务切换与泵窗口来来往往,浮点现场每次被完整存还。这一帧补上,
双 FP 客(RTOS 浮点任务与 Linux 用户态浮点)并存才有底。

## RTOS 本体:两个教科书级的坑

任务内核本体(参考RTOS 公开设计为基准:32 级优先级位图 + tick 轮转)
一次跑通,但两个坑值得记一辈子:

**一、上下文切换函数绝不能标 noreturn。** 我的 `rt_switch_to` 是
异步续跑的:任务 A 调它切给 B,A 冻结在函数里;A 下次被调度时,是
从"调用点之后"回来的。标了 noreturn,GCC 就认为后面是死代码,排
进去的全是循环回头——续跑落进去,第一次是空指针,上一次是落进
了 puts_uart 无限打印。摘掉属性,GCC 排正常收尾,一切干净。

**二、调度器空转必须 WFI。** 壳任务阻塞后调度器选不到人,若不
WFI 就是热自旋——一整个 vCPU 的算力空烧。

## 重头戏:五个藏了十五站的幽灵

这个项目到第十五站为止,VM0 和 VM1 跑的是**同一个裸机镜像的两份
拷贝**。这带来一个天大的巧合:向量表地址、stage-1 配置、GIC 用
法全部相同——于是"每个 EL 共享一份的物理寄存器要在切换时保存"这
件事,十五站从来没暴露过。

第十六站第一天,VM0 换成 RTOS、VM1 留裸机、VM2 跑 Linux,三个
**异构**镜像并跑。幽灵排着队出场:

- **VBAR_EL1(向量表)**:vm1 一引导,物理向量表寄存器就被改成它自
  己的表。vm0 的下一个定时器中断按 vm1 的表跳进错门——执行流掉进
  别的代码里,把 boot 尾三行原样重演了一遍,像鬼打墙。中断日志定
  谳:那些"重演"的输出不是重跑,是错门里的执行流路过。
- **SCTLR/TTBR0/TCR(stage-1 控制面)**:Linux 开着 MMU(M=1+自己的
  页表),RTOS 关着(M=0)。vm0 切回来时,向量取指**穿过 Linux 留下
  的 stage-1 页表**,翻到一个垃圾物理地址,指令中止,VM 死。诊
  断线索妙极了:故障地址(HPFAR)对不上出错 PC 的页——因为取指
  根本没走它自己的翻译。
- **CPACR_EL1(浮点门)**:RTOS 自己开浮点,他客若清零则断腿——
  同类预防,一并收编。
- **ICH_LR0/ICH_VMCR(GIC 虚拟面)**:整颗 CPU 只有一颗 LR0。泵为
  vm0 注入定时器唤醒时,会覆写掉 Linux 尚未认领的 tick——Linux 的
  jiffies 冻死,靴停在首个 msleep。
- **SIMD(浮点寄存器)**:站十四就该做的账,本站清完。

修法一以贯之:全部入 per-VM 帧,泵在进出时前装后存——和站七
vtimer、站十四 sp_el0 同一个家族。**全 EL 共享物理面的 per-VM 化,
是这一站给整个架构补的最后一块结构性地基。**

## 最贵的一课:我造了个调度器,然后把它拆了

门禁要求"RTOS 心跳出现在 Linux 引导流中"。实测第一版判据必挂:
Linux 早期 **PSTATE.I=1**(它自己的中断还关着),我的宿主时间片靠
物理定时器中断递减——中断进不来,时间片永不耗尽,泵单客模式直跑,
活客被饿死。

我造了"陷阱量子":每个 VM 的片除了时间片还限 512 次 MMIO 陷阱,
引导期的中断风暴自己就会把片烧完。这一造,快轮转(40ms 一片)把
宿主相频率拉高两个数量级,撞上一组组合拳:某处理函数会把物理定时
器"关线",而这拍如果落在切换窗口里没被认领——**挂起的中断跟着
物理线走,下一位客一装自己的定时器,线一落,这拍就蒸发了**。Linux
单跑都开始闪断,25% 到 75% 不等。

二分法+对照实验(纯基线 3/3 稳,逐项加回,加到陷阱量子必闪)把责
任钉死。最后我做了正确的决定:**把判据窗口挪到 Linux 解开中断之后
(那时泵自然恢复轮转),然后把这个调度器整个拆掉。** 判据依然成立、
更诚实,而机器回到十五站验证过的形态。
