# 站39 · YouTube 口播稿

**[开场]**
eshine-os 第三十九站,文件系统深面。ramfs 从只读盘活成可写
文件系统,块设备接上真盘。但今天真正想讲的是两颗雷:一颗
是重犯了七个站前的老课,一颗藏在协议设计里。

**[做了什么]**
先说面。ramfs 可写化走写时复制:首次写入时把文件内容从
只读归档拷进一个页池页,之后所有写都落那一页——归档字节
一个不动,构建期打包的 rootfs 永远是只读事实源。建文件
即挂名;删除用死节点标记,不做数组挪移——因为挪移会把
所有还拿着旧索引的打开句柄撕开。枚举走游标协议。SEEK
补齐三档 whence,lseek 按 POSIX 返回新位置——这一改,把
站三十三号写的旧判据当场撞破,加载器的检查同步改成只拒
负值。块设备面:blkdev 成为第四个服务器,后面是真正的
virtio-blk,数据后端就是宿主超级监控器里的静态盘——
站九到十号建好的设备模型,今天兑现红利,一遍跑通。

**[雷一:容量是账]**
第一颗雷要重点讲。通道、连接、名字三张表,容量四、八、
八——那是第三十、三十一站时代按当时用量定的。本站加了
第四个服务器、一个元名、若干瞬时对象,没有人重算:开机
四个服务器恰好把通道表填满,排在后面的每一个 demo 创建
通道都拿到内存不足,整脸溺毙。这个症状被当成雷追了三轮。

七个站前,我们在 ocb 池上交过一模一样的学费,教训原话是
"冒烟前算账"。**容量不是配置项,是账——每加一个占用者,
都要重新合一次。**修法和当年一样:按账放宽,bss 只多一 KB。

**[雷二:回执必须单点]**
第二颗雷在目录枚举。命中分支里写了个 continue,本意是
答完继续收下一条,实际只 continue 了内层循环——游标永远
不增,每个活节点都命中、连环回执;而循环结束后的"越末"
回执最后到达,把之前写好的状态全部覆盖。客户端看到的
永远是零。教训:**多路回执的协议里,任何一路后到都能覆盖
前功;回执必须是单点的——一次处理,恰好一次回执。**

ARM64 Type-1 hypervisor 加 RTOS,Apache-2.0,三十九站。
