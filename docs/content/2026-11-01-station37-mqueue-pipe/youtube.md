# 站37 · YouTube 口播稿

**[开场]**
eshine-os 第三十七站,POSIX 队列族:mqueue、管道、长消息。
今天的主角是一个大家都不陌生的东西——消息传递——外加
一颗绿了三个站的潜雷,和它被定谳的全过程。

**[三件套]**
先说做了什么。mqueue,命名优先级队列:高优先先出,同优先
先进先出,阻塞等待直接复用第十七站建好的 pend 机器——
等待逻辑只建一次,每加一个新同步对象,都是那台机器的
红利兑现日。管道:字节流双端,关键设计是零新 fd 线——
管道服务器就是第三个内核服务器任务,fd 三元组走和串口、
文件服务器一模一样的 wire ops。写端引用全关之后,读恒返
零,这就是 POSIX 的 EOF。长消息:超过六十四字节自动走
一千零二十四字节的长槽池,归还口只有"所有 used 归零的
位置"——生命周期跟着消息本尊走。

**[潜雷]**
然后是本站最好的故事。管道 demo 第一跑必挂:子进程往
管道写,返回负九。排查到服务器侧打探针,现场抓到:fd 层
的写函数,从站三十一号起,就不往消息里填 ocb 这个字段。
为什么三个站都没事?因为串口和文件服务器的写处理,根本
不读这个字段。**一个没人读的契约字段,漏填可以绿很多年。**
第一个真读者——管道服务器要按端分发——上门的当天,
雷爆了;也当天,一行修复,定谳归档。

这条规律值得每个写代码的人记在墙上:契约字段的测试,
唯一的真形式,是找到它的第一个消费者。在那之前,字段
只是碰巧没人看。

**[门禁的账]**
这一站首验门红,查下来两个根因,全在门自己头上。第一个:
源归档是个 gitignore 的构建工件,站三十四号之后没有人
重新生成,bitbake 一直在吃站三十四号的源码树——前面
几轮绿灯,其实全是旧产品混的,参考实现里也有 hello,所以
一直绿。修法是构建脚本每次自愈重生归档,门从此恒验当下
提交树。第二个:yocto 门自己的串口会话,用的是老形状,
attach 之后立刻发命令,撞上注入竞态;补上换行探针和
配对锚,与主流程同律。门会撒谎,有时候是因为门自己
生病。
