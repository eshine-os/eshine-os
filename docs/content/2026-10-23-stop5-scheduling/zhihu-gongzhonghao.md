# 双 VM 第一次真并行:调度站,和一段注释引发的 tick 谋杀案

> 27.04 连载第 5 篇。前三站让 guest 跑起来、两台 VM 并存、每个 vCPU
> 有了完整陷阱帧;第四站宿主第一次活在"被中断"里。这一站回答一个
> 更本质的问题:**单核上,凭什么两个 VM 能同时活?**

## 先说结局:门禁 22 步,spin 跨 7 个量子

    eshine> vmrun 0        ← 立即返回(异步,跑动交给调度泵)
    eshine> vmconsole 0    ← console -> vm0(前台,键盘归 vm0)
    vm0> spin              ← spinning...(纯计算 3G 迭代,约 8 秒)
                          ← 期间被 tick 切走 7 次,又 7 次无损续跑
                          ← spun 3G iters (preempted ok)
    vm0> sleep             ← vm0 让位睡去,vm1 和宿主照常活(公平)
                          ← slept (vtimer irq)(后台轮转中自己醒)
    vm0> host              ← console -> host(主动交还键盘)

每个子系统单独都是对的——帧迁移、tick、键盘、睡眠。拼起来塌了十次。
这一站的 bug 没有一个在"某个模块"里,全部在**模块的交互面**上。

## 设计:shell 就是调度器

先想清楚单核 Type-1 的调度哲学。宿主 shell 是最高优先级任务:
你敲命令时它必须立刻响应(宿主权威),你不敲时它才有空跑别人。所以:

- **shell 等输入的间隙 = 调度泵**。每轮给所有 RUNNING 且非等待的 VM
  各跑一个量子(=1 tick,1 秒),跑完回来看一眼键盘;
- **命令执行期间泵停摆**(原子段)——你不能跑一半 guest 又插进来
  一半宿主命令;
- `vmrun` 异步化:置 RUNNING 立即回 shell。VM 从"阻塞宿主的演示品"
  变成"后台真进程"。

抢占怎么触发?对齐参考实现的形态:**tick 只置标志,真正的切换集中在
trap 出口**。两个扳机点:guest 态 tick 耗尽量子 → IRQ 出口把异常帧
转写进陷阱帧、弃帧走人(与 HVC 退出同构);而 getc 轮询风暴下 tick
多落在宿主段,宿主段代记量子,HVC 出口再查一次。两处合起来,量子
才真正闭合。

## 第一场硬仗:在任意指令边界切走一个 VM

把一个正在 `spin` 里疯狂递减计数器的 VM,从任意指令边界切走、再
无损放回来——调度站的立身判据。第三站攒下的陷阱帧契约在这里兑付:
异常帧逐项转写进 vcpu 帧(gprs 按 asm 偏移契约),ERET 现场完整。

判据设计踩了个坑:最初用"preempts >= 4"(累计值)——错。累计值会被
spin 之前的交互污染,证明不了"**这个负载在这段时间被切走且无损**"。
改成前后差:spin 前读一次 preempts,spin 后再读一次,差 ≥2 才算。
**门禁判据不锚时基,锚跨量子次数**——时基在模拟器上是玄学(TCG 实测
~0.4G 迭代/s,但换台机器就是另一个数),量子数不是。

实测:3G 迭代跨 7 个量子,计数器分毫不差。

## 键盘战争:两个 VM 抢一个键盘

设计时想得很美:guest 直读 UART,谁读到算谁的。实测第一天就被打脸:

**宿主敲的 `vmstat`,落进了 guest 的 shell 执行。** 两个 VM 加宿主,
三双手抢一个 DR 寄存器,输入随机分配——这不是"让位"能救的,
**共享输入面必须有唯一仲裁者**。

修正:键盘所有权(owner=哪个 vCPU,NULL=宿主)。guest 的 getc 走
HVC #3 三态代理:你是 owner,宿主代读真硬件,有字符回字符、没有回
-1;你不是 owner,恒回 -2——guest 见 -2 就 WFI 睡去(陷阱化),泵
顺手去跑别人。前台模式泵只跑 owner,免得俩 guest 拉扯;HVC #4 让
前台 VM 主动交还。输出面(TX)保持直访——第四站的直访成果不丢。

## tick 之死:源码看起来对,汇编不对

本站最狠的一枪。现象:一切正常跑着,tick 在第一次投递后**死了**。
git-bisect 收敛到 exceptions.c——但源码怎么读怎么对。

objdump 反汇编 diff 一眼定案:有一条 if 的两个分支,一个直接
`ret`,一个调 EOI。而 EOI 的调用,在源码里明明是**无条件**的。

回到源码逐字符看:一段多行注释的补丁,把单语句 if 的语句体整个吞
进了注释。if 变成空语句,后一行 EOI 调用在解析上"绑定"进了这个
if。于是宿主空闲段(cur_vcpu 为空)直接 ret——**跳过了 EOI**。
物理中断 26 是电平触发:不撤销,线一直挂着,GIC 认为中断还在,
tick 从此再没来过。

> 教训 1:**单语句 if + 多行注释补丁 = 无声杀手。**
> 教训 2:**源码"看起来对"不等于汇编对。git-bisect 定文件,
> objdump 定罪。源码层面两者已经无法区分。**
> 教训 3:中断子系统对"少一个 EOI"的惩罚方式是全局沉默,不是报错。

## mrs 之谜:计数在走,循环不退

还有一个没破的案,如实交代。时基版 spin(guest 读 CNTVCT_EL0
计时 3 秒)在抢占边界下:计数器以精确速率前进(62.5M/s,正好是
CNTFRQ),所有探针证明帧迁移无损——PC、SP、关键寄存器跨切全稳。
但那个 `cmp/b.lo` 循环,永不落出。15 秒、14 次抢占,计数前进
9 亿,循环纹丝不动。

怀疑是 QEMU mrs helper 与翻译块缓存的交互。判决:**不追**。调度站
的证据已经闭环,不为一口疑气给模拟器开膛。改纯迭代计数(3G 次),
判据换量子差——像上面说的,锚行为不锚时基。QEMU 的这个疑点挂在
devlog 05 里,留给有缘人。

## 睡与醒:公平的代价

WFI 陷阱化(第四站)在这里升级成真"让出 CPU":VM 一睡,泵不再
喂它量子,别人分到的时间立即翻倍——公平不是恩赐,是让位协议的
自然结果。但让位协议必须闭环:**进了等待,就必须放下独占资源**。
第一版前台 VM 睡觉时还攥着键盘:宿主读不到回收命令,泵又被 owner
挡住别人——全系统死等一个永远不来的 WOKE。

还有一枪:虚拟定时器到点时,正在跑的可能是**另一台 VM**。把
"唤醒"记在当值者头上,等待者永不醒、被跑者莫名醒。修复只有一句
话的哲学:**事件的受益者 ≠ 事件的当值者,按状态找人,不按当值
找人。**
