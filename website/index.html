System Architecture

One machine, three domains — designed on two axes: functional safety (ISO 26262) and cybersecurity (ISO/SAE 21434):

  • Type-1 hypervisor · ASIL-D / CAL-4 — direct hardware control at EL2, no host OS; per-VM stage-2 address-space isolation, vGIC / vtimer / virtio device models, CPU & memory quotas, fail-closed cross-VM shared windows; the dual root of trust.
  • VM0 · management domain · ASIL-D / CAL-3 — the from-scratch RTOS: deterministic scheduling, Send/Recv/Reply IPC, fault containment and health monitoring. The safety and security management domain of the system.
  • VM1 · reserved domain · QM / CAL-2 — reserved for the cockpit: planned to boot Android as the center-console / cluster domain.
  • VM2 · Linux domain · ASIL-A/B / CAL-2 — real upstream Linux 6.6 carrying intelligent-driving applications and the musl userland.

ASIL (ISO 26262) and CAL (ISO/SAE 21434) levels are architecture design targets; both certification program is in progress — see the honest boundary statement in KNOWN-ISSUES.md.

Roadmap — in development, by priority

  1. 1
    Functional Safety (ISO 26262) ASIL-D hypervisor/RTOS architecture: fault containment, fail-closed isolation, deterministic scheduling; latency determinism baselines and the certification path.
  2. 2
    Cybersecurity (ISO/SAE 21434) Hardened VM isolation, cross-VM access control, security audit and fuzzing of the virtualization boundary.
  3. 3
    Real-hardware bring-up From QEMU virt to an automotive SoC: SMMU, GIC ITS, real timers and multi-core topologies.
  4. 4
    Deterministic real-time Sub-tick hrtimer wake-ups, partitioned CPU/memory budgets, measured wake-up latency on real hardware.
  5. 5
    Cockpit domain & device ecosystem Bring up Android in the reserved VM1 cockpit slot; virtio net/rng devices; user-space service ecosystem.
