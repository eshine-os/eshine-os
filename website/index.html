Option A — Pinned Docker Image (No Local Toolchain) 
git clone https://github.com/eshine-os/eshine-os.git
cd eshine-os
# Ubuntu 24.04 + cross-gcc + QEMU 8.2.2
scripts/container.sh build
scripts/container.sh run
Supports Podman via ESHINE_CONTAINER_ENGINE=podman. Set ESHINE_CONTAINER_NETWORK=bridge to bootstrap Linux guest artifacts inside the container.
Option B — Native Linux Host (ARM64 Cross-Toolchain + QEMU) 
git clone https://github.com/eshine-os/eshine-os.git
cd eshine-os
# Build binaries & run boot smoke gates (1..18)
make && make verify-fast
make run
Run make verify for the full non-heavy green suite, or scripts/bootstrap.sh --adopt for offline artifact reuse under .work/.

System Architecture

One machine, three domains — structured along functional safety (ISO 26262) and cybersecurity (ISO/SAE 21434) isolation boundaries.

Layer / Domain Design Targets Status Implemented & Planned Capabilities
Type-1 Hypervisor (EL2) ASIL-D / CAL-4 Implemented Direct EL2 hardware control with no host OS; per-VM Stage-2 isolation, vGICv3, vtimer, virtio-blk/net, DTB injection, PSCI VM lifecycle, CPU/memory quotas, and fail-closed cross-VM shared windows.
VM0 · Management RTOS ASIL-D / CAL-3 Implemented From-scratch 2-vCPU SMP RTOS with 32-priority preemptive bitmap scheduler, per-process Stage-1 MMU + ASID, Send/Recv/Reply IPC, futex/signals, ramfs/procfs, HAM health monitor, and musl ELF loader.
VM1 · Cockpit Slot QM / CAL-2 Reserved Currently runs a bare-metal fault-isolation test guest; slot reserved for a future Android cluster / center-console cockpit domain.
VM2 · Linux Domain ASIL-A/B / CAL-2 Implemented Real upstream Linux 6.6 SMP kernel + busybox initramfs + musl userland for perception, planning, and intelligent-driving workloads.
Honest Boundary Statement: ASIL (ISO 26262) and CAL (ISO/SAE 21434) levels are architectural design targets; formal third-party safety certification has not yet started. All automated gates currently execute on QEMU virt (ARM64) — see KNOWN-ISSUES.md for open defects, QEMU 10.2.1 compatibility tracking, and the current security boundary.

Roadmap

Ordered strictly by engineering risk and defect-budget rules: hardware invariants and security boundaries before new surface area.

  1. Next
    EL2 Stage-1 MMU, Security Boundary Hardening & Quarantine Zero Enable EL2 MMU & alignment safety (unblocking QEMU 10.2+), enforce strict RTOS access_ok / W^X / SMP TLB invalidation, align 64-bit spinlock widths, and close the 4 quarantined gates (177/177).
  2. In Progress
    Functional Safety Architecture (ISO 26262) Close remaining SMP dual-core fault families under quiet-window double-green criteria, strengthen fault containment, and formalize traceability from safety requirements to gates.
  3. In Progress
    Cybersecurity Hardening (ISO/SAE 21434) Fuzz the EL2 virtualization and RTOS syscall boundaries, add negative Stage-2 ACL tests, and enforce strict user-copy exception fixups.
  4. Planned
    Real-Hardware Bring-up (Board HAL → SoC) Extract QEMU virt constants into a Board HAL and bring up low-cost ARM64 hardware (Raspberry Pi 5 / RK3588) en route to automotive SoCs with SMMU and GIC-ITS.
  5. Planned
    Sub-Tick Deterministic Real-Time & VM1 Cockpit Domain Add oneshot hrtimer wake-ups with real-hardware wake-up latency histograms, and bring up Android in the reserved VM1 cockpit slot.
